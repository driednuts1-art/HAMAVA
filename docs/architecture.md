# Architecture

Technical decisions actually locked in and built, not just proposed (`product.md` §18). Kept up to date as more of the system is implemented — see `docs/roadmap.md` for what's still deliberately deferred, and `docs/requirements.md` for the per-feature specs this architecture serves.

---

## 1. Stack (locked in)

- **Backend:** NestJS, TypeScript, modular monolith (`product.md` §8.2, §15 sequencing note).
- **Database:** PostgreSQL, hosted on Neon; **Prisma Migrate + Prisma Client** as the ORM/migration tool (chosen over TypeORM — see `docs/roadmap.md`).
- **Auth:** short-lived JWT access token + rotating opaque refresh token, tracked per-device via a `Session` table with revocation support (`product.md` §5).
- **Hashing:** phone numbers and refresh tokens use keyed HMAC-SHA256 (need a deterministic hash for an indexed DB lookup); OTP codes use bcrypt (low-entropy secret, needs slow/salted hashing, no lookup requirement). See the comment in `backend/src/common/crypto/crypto.service.ts` for the full reasoning.
- **API conventions:** `/v1` URI versioning, RFC 7807 problem-details error format, `class-validator` DTOs on every request body (`product.md` §8.2).

## 2. Module structure

```
backend/src/
  modules/
    auth/          — OTP request/verify, JWT + refresh session issuance
    verification/  — biometric consent, liveness challenge lifecycle
    profile/       — profile fields, photo upload/moderation pipeline
  common/
    audit-log/           — append-only trust/security event trail (product.md §9)
    crypto/              — hashing/token primitives
    production-safety/   — see §4 below
    filters/, exceptions/ — RFC 7807 formatting
  prisma/          — PrismaService (driver-adapter based, Prisma 7)
```

Each feature module owns its own external-vendor abstractions (see §3) rather than sharing a generic "providers" grab-bag, so a module's `exports` array is the single place that shows what it exposes to the rest of the app.

## 3. External-vendor abstraction pattern

Every dependency on a real external vendor sits behind a small interface + a NestJS DI token, resolved via `@Inject(TOKEN)`, never referenced by concrete class outside its own module:

| Interface | Token | Owning module |
|---|---|---|
| `OtpProviderInterface` | `OTP_PROVIDER` | `AuthModule` |
| `LivenessProviderInterface` | `LIVENESS_PROVIDER` | `VerificationModule` |
| `StorageProviderInterface` | `STORAGE_PROVIDER` | `ProfileModule` |
| `MalwareScanProviderInterface` | `MALWARE_SCAN_PROVIDER` | `ProfileModule` |
| `ContentModerationProviderInterface` | `CONTENT_MODERATION_PROVIDER` | `ProfileModule` |

Swapping a mock for a real vendor is meant to be a one-line change in the owning module's `providers` array — see `docs/roadmap.md` for the current status (mock vs. real) and blocker (legal vs. implementation-only) of each.

## 4. Production safety guard

`backend/src/common/production-safety/` — every provider above that's still a mock/local stand-in implements a marker (`isMock = true`). `ProductionSafetyService` checks all of them on `onApplicationBootstrap`:

- `NODE_ENV=production` + any mock still wired in → **the server refuses to finish starting**, throws an error naming every mock still in place, exits non-zero.
- Anywhere else → logs a warning and starts normally (mocks are expected in dev/test).

This exists specifically to prevent the failure mode of forgetting to swap a mock before a real deploy — verified working in both directions during Feature 2 review.

## 5. External runtime dependencies (operational)

These are processes/services the backend depends on at runtime, beyond the application code itself.

### 5.1 PostgreSQL (Neon)

Primary datastore for everything. No request completes without it; standard "the database is a hard dependency" reasoning applies, not elaborated further here.

**Serverless cold-start vs. interactive transactions — a real bug hit during Feature 3 development.** Neon's dev branch suspends its compute after a period of inactivity; the first query after a gap pays a cold-start cost (observed: several seconds, occasionally more). Prisma's `$transaction(async (tx) => {...})` (interactive transactions) has its own `maxWait`/`timeout` budget for acquiring a connection and completing — Prisma's defaults are tuned for an always-warm database and are too tight for a cold Neon compute, and failed outright with `Transaction API error: Unable to start a transaction in the given time` during e2e testing after a session gap. Fixed in `backend/src/modules/discovery/swipe.service.ts` (the only interactive transaction in the codebase so far — it wraps the swipe-then-match-creation logic, see Section 3's table) by passing explicit `{ maxWait: 10_000, timeout: 10_000 }`. **Any future interactive transaction added to this codebase needs the same explicit override** — the tight Prisma defaults are the wrong choice against this database, not a one-off fix for this specific call site.

**If it still fails after 10s**, that's a genuine "the database is currently having a bad moment" condition, not something to leak as an opaque 500 — and it's not unique to the swipe transaction. Any endpoint's plain (non-transactional) query can just as easily hit a connection-level Prisma error under the same DB stress (P1001/P1002/P1008/P1017, or P2024 when the connection pool itself is exhausted), not only interactive transactions (P2028). So this is handled **once, globally**, in `ProblemDetailsFilter` (`backend/src/common/filters/problem-details.filter.ts`), not per call site: it maps that fixed set of transient Prisma error codes to a 503 with a "please try again in a few seconds" message (`docs/requirements.md` FR-52), and everything else keeps its existing handling untouched. **No endpoint or service needs its own try/catch for this** — `SwipeService` originally had one, was refactored to remove it once the pattern was clearly going to recur elsewhere. If you're tempted to add a local catch for a Prisma connection error, that's a sign the filter's transient-code set is missing something, not that the call site needs its own handling.

**e2e tests run sequentially against this database by default (`maxWorkers: 1` in `backend/test/jest-e2e.json`), though this specific reason is now historical.** Originally discovered because parallel workers each hitting Neon's **direct** (non-pooled) connection simultaneously produced three different failure modes in one debugging session (the transaction timeout above, a raw `pg-pool` "Cannot use a pool after calling end on the pool" error, and a `findUniqueOrThrow` genuinely finding no row for a user its own test had just created). `DATABASE_URL` has since been switched to Neon's pooled (`-pooler`) endpoint specifically to remove this ceiling, and `--maxWorkers=4` against the pooled endpoint was directly verified clean (zero connection-related failures across the full suite, twice) — see "Known infrastructure debt" in `docs/roadmap.md`. `maxWorkers: 1` remains the checked-in default for now regardless (simplicity, not a hard requirement anymore); this note is kept mainly so the *original* three failure modes are recognizable if seen again, since one of them (a write not visible to a read moments later) resurfaced in a related but not identical form — see the note directly below.

**A related but not fully explained anomaly, surfaced while verifying Feature 9 (unrelated code) and worth recording rather than quietly re-running past**: `test/chat.e2e-spec.ts`'s real-time-WebSocket test intermittently failed twice in a row under today's session — once with a genuine `Foreign key constraint violated on the constraint: messages_matchId_fkey` even though the referenced `Match` had just been read successfully moments earlier in the same request (`ConversationAccessService.assertParticipant()`'s `findUnique` succeeded, the subsequent `message.create()` in the same handler did not, with no explicit transaction linking the two reads/writes) — the same *shape* of anomaly as the historical `findUniqueOrThrow`-finds-nothing case just above, though this session's occurrences were single-worker (`maxWorkers: 1`), not concurrent-worker contention, so the earlier explanation doesn't fully cover this one. On a third attempt the request completed successfully end-to-end (message posted, delivered over the real WebSocket) but the overall test still exceeded its 30s Jest timeout — consistent with today's cumulative real-vendor latency (very heavy same-session OpenAI/ClamAV/Neon usage across many hours of e2e verification work) pushing an already-heavy test (two full verified profiles, each with a real malware scan and moderation call, plus a real match and a real WebSocket round trip) past its timing budget, rather than a functional regression. **Not caused by Feature 9's code** (no swipe/match/message/Redis code was touched building it) and not resolved here — flagged for a real decision (raise this specific test's timeout, and/or investigate whether the pooled endpoint has a genuine consistency edge case under load) rather than silently patched or ignored.

### 5.2 ClamAV (`clamd`) — malware scanning

Real (non-mocked) since Feature 2: `backend/src/modules/profile/moderation/clamav-malware-scan.provider.ts` streams every photo upload to a `clamd` daemon over TCP (ClamAV's INSTREAM protocol) before the file is ever re-encoded or stored.

**This integration is deliberately fail-closed**: if `clamd` is unreachable, times out, or returns an unparseable response, the scan throws (surfaced as a 503) rather than treating the upload as clean. An unscanned upload must never be silently accepted.

**Direct consequence: a `clamd` outage is a complete photo-upload outage**, not a degraded-mode fallback. This is the correct security tradeoff (never accept unscanned content), but it means `clamd` needs to be treated with the same operational seriousness as the database, not as an incidental sidecar nobody watches. Specifically, in production:

- **`clamd` must run as its own container/sidecar**, never colocated as an ad hoc process on the API host the way local dev does today (`C:\ClamAV\clamd.conf`, manually started, database in `C:\ClamAV\db`). A dedicated `clamav/clamav`-style container image (or managed equivalent) with its own resource limits and restart policy.
- **Separate monitoring/alerting for `clamd` itself**, distinct from generic API uptime checks — the API process can report itself healthy while `clamd` is down and every upload is failing underneath it. At minimum:
  - Liveness/readiness probe against the `clamd` TCP port (`CLAMD_HOST`:`CLAMD_PORT`), wired into the orchestrator's restart policy so a crashed `clamd` recovers automatically instead of sitting down until someone notices via user complaints.
  - An explicit alert on upload failure rate / 503s from the malware-scan path, since that's the user-facing symptom of a `clamd` problem.
  - An alert on stale virus definitions — a `clamd` that's up but hasn't had a successful `freshclam` run in its expected interval will keep responding `OK`/`FOUND` based on outdated signatures, which fails silently (no errors, just degraded detection). Track `freshclam`'s last-successful-update timestamp, not just process uptime.
- Config surface is already environment-driven (`CLAMD_HOST`, `CLAMD_PORT`, `CLAMD_TIMEOUT_MS`) — pointing at a production `clamd` instance is an env var change, no application code change.

Called out specifically here because it's the kind of dependency that's easy to treat as "just another thing that's probably fine," colocate without much thought, and under-monitor — which would silently defeat the fail-closed design at exactly the moment it matters.

### 5.3 Redis (Upstash) — chat WebSocket pub/sub

Real (non-mocked) since Feature 4: `backend/src/common/websocket/redis-io.adapter.ts` backs the chat gateway's Socket.IO server with `@socket.io/redis-adapter`, so `server.to(room).emit(...)` reaches a client connected to a different backend instance (`product.md` §8.4, `docs/requirements.md` FR-59). Verified working end-to-end with a real socket.io-client in `test/chat.e2e-spec.ts` — a message POSTed via REST actually arrives over a live WebSocket, not just "the code compiles."

**Important historical correction, added during Feature 17 (2026-08-24) — read alongside §5.11's own correction below, they're the same underlying bug.** The paragraph above was wrong in a specific, narrow, but real way: `test/chat.e2e-spec.ts`'s delivery test *did* prove a REST-posted message reaches a live WebSocket client — but it never actually proved that delivery went *through Redis*, because that test has always run a single app instance, and a single-process Socket.IO server delivers a same-process room event identically whether or not `server.to(room).emit()` is backed by the real Redis adapter or Nest's plain in-memory default. The two are indistinguishable from inside one process. Combined with the real wiring bug §5.11 documents (`RedisIoAdapter` was never actually bound to the gateway at all, on any instance, from this feature's introduction through Feature 17), the practical reality is: **`RedisIoAdapter` had been present in the codebase, correctly implemented, correctly unit-tested, and completely inert in every environment this app has ever run in — dev, every e2e suite, and any real deployment — for thirteen features' worth of this project's life**, without a single test ever being structurally capable of catching it. A real, genuine gap between "verified" and "actually exercised," not a small thing to gloss over. Closed for real in Feature 17: `test/chat.e2e-spec.ts`'s new `describe('Redis pub/sub — real cross-instance delivery (FR-59)', ...)` block boots two fully independent app instances on two real ports, connects a client to instance B, and sends the message through instance A's REST API — the *only* path from A to B is the real Redis channel, since A's own in-process Socket.IO server has no other way to know instance B's socket exists. Confirmed to actually catch the historical bug, not just pass by construction: deliberately reintroduced the exact original ordering mistake, re-ran the suite, and watched this new test fail with a real 30s delivery timeout while the file's other three (single-instance) tests kept passing — proof the new test detects specifically what the old ones structurally could not.

**A real bug hit during Feature 4 development, worth remembering exactly because it looked like something else at first**: after the e2e suite finished and printed a passing/failing result, the Node process kept running indefinitely — for one debugging session, over an hour, before being killed and diagnosed. It looked like a hang *during* the test. It wasn't. Jest's own "did not exit one second after the test run has completed... asynchronous operations that weren't stopped" warning was the actual signal, printed immediately after results — the process was stuck *after* finishing, not stuck *while* running. The cause: `RedisIoAdapter`'s two redis clients (`pubClient`, `subClient`) are plain `redis` package clients, not Nest-managed providers, so `app.close()` has no idea they exist. `node-redis`'s default reconnect strategy retries forever, so a process that never explicitly closes them never exits on its own — it sat in a silent `ECONNRESET` / `ENOTFOUND` / `Connection timeout` retry loop.

**Fixed, not worked around**: `RedisIoAdapter.close()` calls `.quit()` on both clients. `test/chat.e2e-spec.ts`'s `afterAll` calls it before `app.close()`. `main.ts` calls it from a `SIGTERM`/`SIGINT` handler before the real server exits, for the same reason in production — a graceful shutdown needs to release these too, not just the HTTP server.

**Anything that manually constructs a client/connection outside Nest's DI lifecycle inherits this exact risk** — the fix pattern (an explicit `close()`, called by both the app's shutdown path and every test that constructs one) is the thing to repeat, not just this one adapter.

**Two follow-up questions after the fix, and what verifying them actually found**: (1) does the `main.ts` `SIGTERM`/`SIGINT` handler really run on a real signal, and (2) if `redisIoAdapter.close()`'s `.quit()` itself hangs (e.g. a network issue), is there a fail-safe that forces exit rather than reproducing the same hang.

- **Fail-safe timeout — verified directly.** `main.ts` races `redisIoAdapter.close(); app.close()` against an `.unref()`'d `setTimeout(SHUTDOWN_TIMEOUT_MS)` (same pattern as the ClamAV fail-closed design and the Prisma `$transaction` `{maxWait, timeout}`). Tested in isolation with a *realistic* hang — a real TCP `connect()` to a non-routable address, which never resolves and holds a real OS handle open, unlike a bare dangling `Promise` (which has no handle to keep the event loop alive and produced a misleading first result). Against the real stuck handle, the timeout branch won at ~2016ms against a 2000ms ceiling and the process proceeded to `process.exit(0)` instead of hanging. This part of the fix is confirmed working.
- **Real cross-process `SIGTERM` delivery — not verifiable on Windows, but since verified on real Linux, and confirmed working.** Three attempts to send a real `SIGTERM` from a separate process to a running server on this Windows/Git-Bash machine all failed to trigger the handler's log output, including one that specifically ruled out tool-latency and a Git-Bash/MSYS PID-namespace mismatch (bash's `$!` reports a different PID than Node's own `process.pid`) as red herrings — the target process exited (with the POSIX "killed by signal 15" exit code, 143) without the handler's log line ever printing, meaning it was very likely hard-terminated by Windows before the JS event loop got to run the callback. Consistent with Windows not having real POSIX signals.

  **Resolved by testing on an actual Linux kernel instead of guessing it would work there.** Docker itself isn't installed on this dev machine, but WSL2 was already present (`wsl --status` showed an existing Ubuntu distro) and is a genuine Linux kernel, not an emulation — confirmed directly (`uname -a` → `Linux ... microsoft-standard-WSL2 ... GNU/Linux`). One real obstacle along the way: WSL's own outbound network turned out to be blocked in this sandbox (`apt-get update` and a direct `curl` to `archive.ubuntu.com` both timed out), so `apt install nodejs` wasn't an option — worked around by downloading the official Linux x64 Node binary from the Windows host (which has working internet, used throughout this project for Neon/Upstash/OpenAI/npm) and extracting it inside WSL via the shared `/mnt/c/` filesystem.

  **The first pass at this test used a hand-typed reconstruction of `main.ts`'s shutdown logic run manually — a real gap, since it proved the *pattern* works on Linux but not that `main.ts` itself does, and left nothing repeatable for CI.** Both problems came from the same fix: the shutdown orchestration was extracted out of `main.ts` into a standalone, exported `registerGracefulShutdown()` (`backend/src/common/graceful-shutdown.ts`), so there is exactly one implementation — `main.ts` calls it for real, and the tests exercise the same function directly, not a copy of its logic. Two permanent tests now cover it, both runnable in CI, not one-off:
  - `backend/src/common/graceful-shutdown.spec.ts` — a platform-independent unit test of the pure timeout-race/single-fire-guard logic (fake timers, an injectable `exit` callback so it never actually kills the test process). Runs everywhere, including Windows.
  - `backend/test/graceful-shutdown-signal.e2e-spec.ts` — spawns `backend/scripts/graceful-shutdown-probe.ts` (which imports the real `registerGracefulShutdown`, not a reconstruction) as a genuine child process and sends it real `SIGTERM`/`SIGINT` via `child.kill()`, asserting on its stdout markers and exit code. Platform-gated (`describe.skip` on `win32`) so it's a clean no-op on Windows dev machines and genuinely runs on Linux/WSL/CI.

  Getting this permanent test running for real (not just written) surfaced three genuine, unrelated bugs, each fixed rather than worked around:
  - Copying `node_modules` from the Windows install into WSL silently broke `ts-jest` because an over-broad `tar --exclude=dist` matched *every* `dist/` folder in the tree (`node_modules/ts-jest/dist` included), not just the project's own build output — fixed by scoping the exclude to `./dist`.
  - Jest 30's resolver (`jest-resolve`, via `unrs-resolver`) uses a native Rust binding shipped as a platform-specific optional dependency; `npm install` on Windows only fetches the Windows one, so the plain copy was missing `@unrs/resolver-binding-linux-x64-gnu` and every module resolution silently returned `null` (Jest's own error swallowing hid the real cause — traced by temporarily patching `jest-resolve`'s catch block to log it). Fixed by downloading that one platform package from the npm registry via the Windows host's internet and extracting it into the WSL copy.
  - The probe process was exiting cleanly before ever reacting to a signal, on the very first version: a bare `process.on('SIGTERM', ...)` does **not** keep Node's event loop alive by itself (verified empirically with a two-line repro) — `main.ts` stays alive because of the real HTTP server from `app.listen()`, which the stubbed probe has no equivalent of. Fixed by adding an explicit ref'd `setInterval` keep-alive to the probe.
  - Even after that, signaling immediately upon seeing the probe's readiness line was flaky specifically with a *warm* ts-node compile cache (cold-cache runs, several seconds long, never failed): the entire module-load-to-registered-handler sequence can complete in under 2ms, faster than the OS reliably arms the new `sigaction()` before a signal sent that quickly arrives, so the default (process-terminating) disposition sometimes won the race. Fixed with a short (300ms) settle delay in the test between seeing readiness and sending the signal — irrelevant to `main.ts` in production, whose real bootstrap (DB/Redis connections, HTTP listen) always takes far longer than this window.

  With all of that fixed, `test/graceful-shutdown-signal.e2e-spec.ts` was run three consecutive times on the real Linux Node binary inside WSL and passed cleanly every time — `SIGTERM`, `SIGINT`, and the fail-safe-timeout branch (a deliberately hung `onShutdown` forced past its ceiling) all produced the exact expected log lines and exit code `0`, with zero flakiness. `main.ts` itself needed no further changes beyond the extraction — the actual deployment target (containers/systemd/PaaS) needed no code change, only a real kernel and a real, permanent test to prove it against.

### 5.4 MinIO — S3-compatible object storage (photos)

Real (non-mocked) since the post-MVP "Real Photo Storage" hardening pass (`docs/requirements.md` Feature 7): `backend/src/modules/profile/storage/s3-storage.provider.ts` talks to any S3-compatible endpoint over the standard protocol (`@aws-sdk/client-s3` / `@aws-sdk/s3-request-presigner`) — the same code runs against MinIO here and against a real cloud vendor in production, differing only by `STORAGE_*` env vars.

**Why local MinIO instead of a cloud signup, reversing the Neon/Upstash precedent**: Neon and Upstash were chosen as cloud services specifically because native Windows support for Postgres and especially Redis is genuinely poor (Redis has no official Windows build at all). That reasoning doesn't transfer to MinIO, which ships an official Windows binary — checked directly rather than assumed: `winget install MinIO.Server` completed with no config file and no service-registration step, and `minio.exe server <path>` started a working server on the first try, verified with a real HTTP request (`curl` against `/minio/health/live` and the bucket root, both returning genuine S3-protocol responses). Simpler than `clamd`'s Windows setup, which this project already accepted as a real local install.

**Local dev setup**: `minio.exe` runs as a persistent local process (data at `C:\MinIO\data`, API on port 9010, console on 9011). A dedicated `hamava-photos-dev` bucket holds all dev/test photos — one bucket shared between manual dev use and e2e runs, the same pattern already used for the shared Neon dev database. The app authenticates as a **least-privilege app user** (`hamava_app`, created via `mc admin user add` + a bucket-scoped IAM policy), not MinIO's root credentials — root stays in `C:\MinIO\root-credentials.env`, outside the repo, used only for one-time admin setup (bucket/user/policy creation via `mc`), never referenced by the running app.

**Presigned URLs, not permanent public links**: `getUrl()` returns a time-limited, signed URL (`PHOTO_URL_EXPIRY_SECONDS`, default 900s) generated fresh on every API response — the URL is never persisted, so there's nothing to invalidate if the expiry policy changes later. Verified directly, not assumed: `test/storage.e2e-spec.ts` fetches the same URL string before and after its (short, test-only) expiry window and confirms the storage backend itself rejects the expired one with a real `403` — proving the signature actually expires, not just that the URL "looks" presigned.

**The `hamava_app` least-privilege scoping is verified by trying denied operations for real, not by reading the policy JSON back.** The policy existing and being attached (confirmed when it was created) proves nothing about whether it actually confines anything — a typo'd resource ARN or an over-broad action list would still look correct on paper. `test/storage.e2e-spec.ts`'s second describe block creates a real foreign bucket with real root credentials, then uses the app's actual credentials to attempt: writing into it, reading from it, deleting it, creating an entirely new bucket, and listing all buckets (confirming the foreign one never appears) — every one denied with a genuine `AccessDenied` from MinIO itself. Caught one real bug while writing this: a first version of the "deny bucket creation" test used a bucket name long enough to exceed S3's 63-character limit, which MinIO rejects as `InvalidBucketName` *before* the IAM policy is ever evaluated — that would have "passed" without proving anything about the actual permission boundary. Fixed by keeping the probe bucket name short and otherwise valid, so a pass means the policy denied it, not that the request was malformed.

**Verified against a real cloud S3-compatible vendor (Cloudflare R2), not just MinIO.** MinIO alone only proves the code works against one S3-compatible implementation; `docs/requirements.md` Feature 7 §9 required a second pass against a real vendor before Storage counts as fully production-ready, since S3-compatible services aren't perfectly interchangeable in practice (signature/checksum-header handling and bucket-addressing style are known sources of divergence). Real R2 credentials (account-scoped access key, `STORAGE_REGION=auto`, `STORAGE_ENDPOINT` pointed at the account's `*.r2.cloudflarestorage.com` endpoint) were swapped into `backend/.env` temporarily — the only file the credentials were ever stored in, per instruction, and gitignored throughout — and the real S3-protocol code path ran unmodified against them:

- `test/storage.e2e-spec.ts`'s presigned-URL tests (real save → real presigned `getUrl()` → real `fetch` returning `200` before expiry and a real `403` after it, plus the SigV4 signature-shape check) — **2/2 passed**.
- `test/profile.e2e-spec.ts`'s full real pipeline (upload → ClamAV scan → OpenAI moderation → image re-encode → R2 store → API-returned URL fetched directly → delete verified to actually remove the object from storage, not just the DB row) — **6/6 passed** on a clean run.
- `test/discovery.e2e-spec.ts`, `test/chat.e2e-spec.ts`, `test/report-block.e2e-spec.ts` — all of which assert on real, fetchable photo URLs in their responses — **11/11 passed**.

One real hiccup during this, reported rather than glossed over: an earlier pass through `profile.e2e-spec.ts` hit a genuine `503` on one upload (the "actually removes the file from storage on delete" test, the 6th and last real upload in that file). Diagnosed before concluding anything: `ServiceUnavailableException` in this codebase comes only from the ClamAV or OpenAI moderation providers' fail-closed paths (§5.2, §5.5) — never from the storage layer itself, which has no such wrapping — so this couldn't be an R2 defect by construction. Re-run twice to check reproducibility: the single failing test alone passed clean in isolation, and the full six-test file passed clean end-to-end on a second full run (25.8s vs. the first run's 83.4s, consistent with transient ClamAV/OpenAI contention under six back-to-back real calls in one file, not a storage-layer bug — the same category of local-dev flakiness already documented in §5.5 for these two dependencies, just this time transient rather than "process died").

**Not run against R2**: the least-privilege cross-bucket-denial sub-test (`storage.e2e-spec.ts`'s second describe block). That test needs *admin-level* credentials to provision a disposable foreign bucket the app credentials should then be denied access to — for MinIO that's the separately-held root user; for R2 it would mean a Cloudflare account-level API token, which wasn't provided (the one R2 credential set given is the already-scoped app-level access key, the equivalent of `hamava_app`, not R2's account root). This specific boundary is still proven — against MinIO, via the identical S3-protocol code path (§ above) — just not re-proven against R2 specifically; doing so would need those additional account-level credentials if ever wanted.

After verification, `backend/.env`'s `STORAGE_*` vars were reverted to the MinIO values for continued local dev (re-confirmed working: `storage.e2e-spec.ts`'s full 7-test suite, both describe blocks, passed clean against MinIO immediately after the revert) — R2 was a real, temporary, credentialed pass to prove production-readiness, not a switch of the local dev backing store.

### 5.5 OpenAI Moderation API — content moderation (text + image)

Real (non-mocked) since the post-MVP "Real Content Moderation" hardening pass (`docs/requirements.md` Feature 8, the second and final "unblocked mock" item): `backend/src/common/moderation/openai-content-moderation.provider.ts` calls OpenAI's Moderation API (`omni-moderation-latest`) directly over `fetch` — no vendor SDK. One model handles both `moderateText()` (a plain string) and `moderateImage()` (a `data:` URI content item), matching `ContentModerationProviderInterface`'s existing shape unchanged.

**A real key-validity puzzle, worth remembering exactly because the obvious diagnosis was wrong**: the first live smoke test returned a persistent `429 Too Many Requests` on `POST /v1/moderations`, while `GET /v1/models` succeeded with the exact same key — ruling out an invalid/revoked key. Traced to OpenAI billing not yet being active on the project; once enabled, the same requests succeeded immediately. Checked, not guessed: three spaced-out retries confirmed the 429 wasn't a transient burst limit before concluding it was account-level, and the cross-endpoint comparison (`/v1/models` vs `/v1/moderations`) is what actually isolated it to something moderation-specific rather than a general auth problem.

**Fails closed**, exactly mirroring `ClamAvMalwareScanProvider`'s pattern: a network error, timeout, non-2xx response, or unparseable body all throw `ServiceUnavailableException` (503) — unscanned content is never silently treated as approved.

**The human review queue (`ModerationFlag`) is the harder half of this feature, not the vendor swap.** Before Feature 8, a moderation rejection left no trace beyond a 422 response and an audit-log line — the content itself was never persisted anywhere, so there was nothing for a review queue to actually show. Every rejection now creates a `ModerationFlag` row retaining the real content: bio/message text stored directly, a flagged photo's already-processed bytes quarantined under a `flagged/` prefix in the same bucket Feature 7 built (via `STORAGE_PROVIDER`, not a second storage system). `GET`/`PATCH /v1/admin/moderation-flags` is a direct reuse of Feature 5's `AdminGuard` + cursor-pagination + resolve pattern — deliberately not a new design. Resolving a flag (`UPHELD`/`OVERTURNED`) only records a human's verdict; it does not republish the content, the same "review is not enforcement" boundary Feature 5 drew for report resolution.

**Verified against the real API, not a mock**: a benign string and a genuinely threatening one were both correctly classified before any application code was built on top of the integration; a real 64×64 WebP round-tripped successfully (a degenerate 1×1 test pixel triggered a real `500` from OpenAI's own side first — a sign the input was unrealistic, not that the integration was broken, since no real upload is ever that small). `test/moderation.e2e-spec.ts` sends real threatening text through the actual HTTP API for both a profile bio and a chat message, confirms each is genuinely rejected by the live vendor and retained as a `ModerationFlag`, and drives the admin list/resolve endpoints against those real flags. Photo-quarantine and fail-closed behavior use a substituted provider instead — reliably forcing a real vision classifier to flag a synthetic test image isn't practical, and isn't an appropriate thing to embed as a fixture for the nudity/violence categories specifically — but the quarantine write itself still goes through real MinIO, so only the verdict is faked, not the storage mechanics around it.

**A local-dev diagnostic detour, worth documenting so it doesn't cost time twice**: partway through writing `test/moderation.e2e-spec.ts`, both `clamd` and MinIO turned out to have stopped running — enough real wall-clock time had passed since they were started earlier in the same work session that both manually-launched processes were simply gone, with nothing supervising or restarting them. Every photo-upload request failed closed with a 503 regardless of the moderation logic itself, which briefly looked like a Feature 8 regression until `curl http://127.0.0.1:9010/minio/health/live` and `netstat` against port 3310 directly confirmed neither was listening. Both are local-only conveniences (production runs each as a real managed service/sidecar, per §5.2/§5.4), but worth remembering: **if a moderated-upload or storage request starts failing closed for no apparent code reason on this dev machine, check whether `clamd`/MinIO are still actually running before suspecting the application code.**

### 5.6 pgvector + OpenAI (extraction/embeddings/Whisper) — AI Prompt Search

Real (non-mocked) from the start, unlike every vendor above: `docs/requirements.md` Feature 9 built directly against real OpenAI calls rather than starting from a mock and swapping later, since a text-extraction/embedding/transcription mock would have nothing meaningful to stand in for. `backend/src/modules/discovery/ai-search/` holds three real providers — `OpenAiExtractionProvider` (`gpt-4o-mini`, OpenAI Structured Outputs, `/v1/chat/completions`), `OpenAiTranscriptionProvider` (`whisper-1`, `/v1/audio/transcriptions`, Persian forced via `language: "fa"`), and `OpenAiEmbeddingProvider` (`text-embedding-3-small`, 1536 dimensions, `/v1/embeddings`, shared with `ProfileService` via a `@Global()` `AiEmbeddingModule`) — all `fetch`-based, no SDK, all failing closed exactly like `OpenAiContentModerationProvider`.

**pgvector on Neon was verified empirically before any implementation depended on it**, per this project's standing rule (the same discipline as the Neon pooled-connection research): `pg_available_extensions` confirmed `vector` 0.8.6 with `ivfflat`/`hnsw` access methods available, `CREATE EXTENSION vector` succeeded, and a real temp-table cosine-distance query ranked three known vectors in the mathematically correct order — checked through both the direct and pooled connection strings, since the app's actual runtime queries go through the pooled one. `prisma/schema.prisma` declares `previewFeatures = ["postgresqlExtensions"]` and `extensions = [vector]`; `User.bioEmbedding` is `Unsupported("vector(1536)")` (Prisma has no native vector type, so it's read/written only via `$queryRaw`/`$executeRaw`), with a hand-written `hnsw`/`vector_cosine_ops` index appended to the generated migration SQL (Prisma's schema DSL can't express a vector index).

**The verified-only floor (FR-47) is protected structurally against this feature's new attack surface, not just by convention.** A natural-language prompt is a new kind of input feeding into a filter that gates account-level safety — `OpenAiExtractionProvider`'s response JSON schema (OpenAI Structured Outputs, `strict: true`) simply has no field capable of expressing "include unverified users," and `AiSearchDto` has no `verifiedOnly` field either; `verifiedOnly` is read only from the caller's own standing `DiscoveryPreferences`, the same source `DeckService` already used. Verified for real, not just unit-tested: an e2e test sends a real prompt explicitly asking to include unverified users through the real extraction endpoint, confirms the real response has no such field, and confirms the real search still excludes an unverified seeded candidate.

**The hard-filter/exclusion logic is one implementation, not two.** `DeckService`'s exact safety-exclusion `where` clause (self, incomplete profiles, already-swiped, blocked, the FR-79 messaging-permission gate) was extracted into `buildSafetyExclusionWhere()` (`backend/src/modules/discovery/candidate-exclusion.util.ts`) and both `DeckService.getDeck()` and `AiSearchService.search()` now call it — a fix here fixes both callers, and there's no way for the two to silently drift apart.

**Ranking keeps raw SQL to the smallest possible surface, deliberately.** The hard-filtered candidate *ID list* is produced entirely through Prisma's normal, type-safe query builder — every relational condition (blocks, swipes, messaging permission) stays outside raw SQL. Only the ranking step itself is raw SQL: a parameterized `Prisma.sql` template (never string concatenation — the first raw-SQL query this codebase has needed, and the precedent it sets was treated as deliberately security-sensitive) that computes `COALESCE("bioEmbedding" <=> :queryVector, 'Infinity'::float8)` per candidate and orders by it. That `COALESCE`-to-`Infinity` trick does double duty: it's how a candidate with no embedding yet sorts after every ranked one without a separate `NULLS LAST` clause, *and* it's what makes a plain three-part tuple comparison (`(distance, createdAt, id) > (cursor...)`, using Postgres's native row-comparison operator) work as the keyset-pagination cursor condition — `cursor.util.ts` was extended with `encodeRankedCursor`/`decodeRankedCursor` for this `(distance, sortKey, id)` triple rather than growing a second, parallel pagination utility.

**Verified directly against real Neon before any application code was built on top of it** (not assumed from how the SQL reads): a standalone script seeded four real users with real, hand-constructed embedding vectors (one identical to the query vector, one 95%-similar, one orthogonal, one left `NULL`), ran the exact ranking query, and confirmed the returned order and distances were mathematically exactly right (`0`, `≈0.0014`, `1`, `Infinity`) — and that paginating across two pages of that same result set returned all four exactly once, in the same order, with no duplicates or gaps.

**Candidates never disappear for lack of an embedding — a deliberate design reversal, not an edge case patched in later.** The original draft excluded un-embedded candidates from AI-search results entirely; reviewed and reversed, because a brand-new user (or anyone who hasn't touched their bio since this feature shipped) would otherwise be invisible to AI Prompt Search specifically — directly working against the product's core "be seen" goal. They're still returned, just unranked, appended after every semantically-ranked candidate. `ProfileService.updateProfile()` recomputes `User.bioEmbedding` synchronously in the same request that already calls `moderateText()` on bio changes (one more real OpenAI call in an existing flow, not a new background-job system) — and is deliberately **resilient, not fail-closed**, here specifically: if the embedding call fails, the profile save still succeeds and only logs a warning, since failing a user's bio edit over an unrelated ranking feature's vendor hiccup would be a worse outcome than a stale embedding that self-heals on the next edit. `scripts/backfill-bio-embeddings.ts` is the one-time catch-up for users who predate this feature — **run for real against the actual dev database**, not just written and assumed to work: found 0 candidates initially (checked directly — genuinely zero existing users had a `bio` set, not a script bug), then a real bio was set on one real user, the script computed and wrote a real 1536-dimension embedding (confirmed via `vector_dims()`), a second run correctly found nothing left to do (idempotency confirmed), and the test data was reverted afterward.

**Audio is never persisted anywhere, checked, not just designed that way**: `POST /v1/discovery/ai-search/transcribe` uses the same in-memory `FileInterceptor` buffer pattern as photo upload, and the buffer is never written to a temp file, the database, or `STORAGE_PROVIDER` — verified in `test/ai-search.e2e-spec.ts` by listing the real MinIO bucket's object count before and after a real transcription call and confirming it's unchanged, and by confirming the `AiSearchRequest` row created for rate-limiting has no column that could hold audio bytes in the first place.

**A real Persian speech fixture, generated (and verified) via the same OpenAI account, not a synthetic/silent file**: `test/fixtures/ai-search-prompt-fa.mp3` was produced once via OpenAI's TTS endpoint (`/v1/audio/speech`, `tts-1`) reading the project's own example search prompt aloud, then immediately round-tripped through the real Whisper endpoint to confirm it transcribes back to recognizably the same sentence before being committed as a fixture — satisfying the explicit standard that at least one test must connect to Whisper with a real audio file, not a mock.

**Two real bugs the e2e suite caught before this counted as done, both fixed rather than glossed over**: (1) the endpoint path for blocking a user in the exclusion test was guessed wrong (`/v1/safety/blocks` instead of the real `POST /v1/users/:userId/block`) — caught by a real `404`, not assumed correct from memory. (2) The vendor-failure fallback test's first two attempts both produced false results in opposite directions — the first passed vacuously because the search's hard-filtered candidate pool was empty (no real candidate had been seeded, so the code legitimately short-circuited at the empty-result path before ever reaching the embedding call it was supposed to test), and after seeding a candidate, the *viewer* itself was left unverified, which silently emptied the pool again via the FR-79 messaging-permission gate for a different reason. Once both were fixed, a third attempt still surfaced a genuine `500` instead of the expected `503`, traced to the test's own mock throwing a bare `Error` instead of the `ServiceUnavailableException` the real `OpenAiEmbeddingProvider` actually throws on failure — `withDeckFallbackHint()` (`vendor-failure.util.ts`) correctly leaves non-`ServiceUnavailableException` errors alone (surfacing a real bug as a real `500`, not silently repackaging it as "vendor down"), so the bug was in the test's fidelity to the real failure shape, not in the fallback logic itself. All ten tests in `test/ai-search.e2e-spec.ts` pass cleanly against real OpenAI and real Neon/pgvector after these fixes.

### 5.7 Super Like explanation, "Why You Two?", Smart Boost (Feature 10)

`backend/src/modules/discovery/match-explanation/` holds `MatchExplanationService` (the fail-open orchestrator) and `OpenAiMatchExplanationProvider` (the real vendor calls — `generate()` a plain chat completion, `checkGrounded()` a strict OpenAI Structured Output). Both `SwipeService` (Super Like, synchronous) and `MatchService` (lazy "Why You Two?" on first `GET /v1/discovery/matches`) call only `MatchExplanationService.generate()` and never see the two-call mechanics.

**Generation is verified by a second, independent real call, not trusted on its own (FR-119).** A model that hallucinated a claim is not a reliable judge of its own hallucination, so `checkGrounded()` is a separate structured-output call — `{ grounded: boolean, unsupportedClaim: string | null }` — checked before the explanation is ever persisted or returned. A rejection is treated exactly like a generation failure: fail-open, `null`, never surfaced, never blocks the swipe or match read.

**A real calibration bug was found and fixed before this counted as done.** The first version of `GROUNDING_CHECK_SYSTEM_PROMPT` demanded near-literal fact matching and flagged legitimate paraphrases as fabrication — e.g. synthesizing "کوهنوردی" (hiking) and "طبیعت‌گردی" (nature touring) into "a shared love of nature" was wrongly rejected, which would have made the feature nearly non-functional in practice (nearly every real generation discarded). Found via a standalone, repeatable probe script (`ts-node`, run directly against the real OpenAI account, deleted after use) rather than inferred from a failing test — confirmed the over-rejection, then confirmed the fix resolved it without over-correcting (a genuinely fabricated claim, re-tested after the fix, still correctly returns `grounded: false`). The rewritten prompt explicitly distinguishes "reasonable paraphrase/synonym/gloss of something real" (grounded) from "information with no basis in either profile at all" (not grounded), with an explicit "if in doubt, prefer grounded" instruction — this check exists to catch real hallucination, not to penalize normal phrasing of the same real facts.

**Even after that fix, a rejected generation is still a normal, expected outcome — not a bug — and two e2e tests were wrong to assume otherwise.** Generation is non-deterministic: the exact same two profiles can produce a safely-phrased explanation on one call and an over-claiming one (correctly discarded) on the next. Both `test/match-explanation-boost.e2e-spec.ts`'s Super Like test and its lazy-"Why You Two?" test originally asserted the resulting explanation is unconditionally truthy, which made them genuinely, correctly flaky — not a race condition or an infrastructure fluke, but the fail-open safety mechanism doing exactly its job on a borderline real generation. Root-caused with the same rigor as the Feature 9 investigations: NestJS's `Logger.warn()` calls placed inside `MatchExplanationService` for debugging did not reliably surface in Jest's captured e2e output (a still-unexplained quirk of this specific test harness, not chased further once a more direct method worked), so the investigation switched to raw `fs.appendFileSync` debug logging that bypasses Jest/Nest entirely — which caught the real sequence directly: `generate()` producing a plausible-sounding sentence attributing "کوهنوردی" to *both* users when only one had listed it, `checkGrounded()` correctly flagging that as unsupported, `null` correctly propagating to `Swipe.aiExplanation`. Fixed by rewriting both tests to retry against a fresh candidate pair up to 3 times, accepting the first non-null result — proving the real generate→check→persist wiring works, without asserting that every individual real generation must pass grounding (three consecutive real rejections would itself indicate a genuine regression, and both tests still fail loudly if that happens). Confirmed stable across 5 consecutive full clean runs (9/9) after the fix.

**The FK/dating-intent ordering rule (FR-43) is easy to get backwards when writing a new test, not just when writing new code.** `Match.source` is set by the *completing* (second, mutually-reciprocating) swipe's action, not the first one — an e2e test for "Super Like completes a match" initially had the Super Like as the *first* swipe, which under FR-43 correctly produces `source: 'SWIPE'`, not `'SUPER_LIKE'`, and the test's own assertion was wrong, not the code. Fixed by re-reading FR-43's original text rather than guessing, and swapping the swipe order (plain LIKE first, Super Like second/completing).

**Smart Boost's reciprocal check is the first check in this codebase to run in the reverse direction.** Every prior filter (deck hard-filters, AI search) checks "does the candidate satisfy the viewer's preferences." `viewerSatisfiesPreferences()` (`deck.service.ts`) is the first to check "does the viewer satisfy the *candidate's* (booster's) own preferences" — a boosted candidate is only promoted in the viewer's deck if the viewer would also pass the booster's own filters, so boost can't force a visibility mismatch neither side actually wants. Both directions are covered by dedicated tests, not just the promotion path: a positive case (booster's preferences satisfied → promoted ahead of an earlier candidate) and a negative case (booster wants an age range the viewer doesn't fall in → *not* promoted, plain chronological order preserved) — the negative e2e test originally only asserted the boosted candidate was visible, which doesn't prove promotion was denied; fixed to assert the earlier plain candidate still precedes it.

**Boost tiering reuses Feature 9's ranked-cursor utility for a non-vector case.** `DeckService` fetches a bounded candidate pool (`MAX_CANDIDATES_TO_TIER = 2000`, same instinct and same accepted scale limitation as Feature 9's `MAX_CANDIDATES_TO_RANK`), tiers it in application code (`tier: 0` boosted-and-reciprocal, `tier: 1` everyone else — no vector math needed, so no raw SQL needed either), and cursor-paginates via `encodeRankedCursor`/`decodeRankedCursor`'s `(distance, sortKey, id)` triple with `tier` standing in for `distance`.

**The Prisma-migration/hand-written-index conflict recurred, confirming it's a standing gotcha, not a one-off.** As with Feature 9's HNSW index, this feature's migration diff (`npx prisma migrate dev --create-only`) generated a spurious `DROP INDEX` for that same hand-written vector index, because Prisma's schema DSL still can't see it. Manually removed from the migration SQL before applying (via `migrate deploy`, not `migrate dev`, to avoid the interactive migration-name prompt); the index's survival and the new columns/table were verified directly with a raw `pg` query, not assumed from the migration succeeding. **This will recur on every future migration** until the vector index is expressed some other way — check the generated SQL for a stray `DROP INDEX` on `users_bioEmbedding_hnsw_idx` every time.

### 5.8 Conversational (text+voice) Profile Setup (Feature 11)

`backend/src/modules/profile/conversational-setup/` — a new entry path into Feature 2's existing profile fields, not a replacement for `PATCH /v1/profile`. Reuses Feature 9's exact Whisper transcription pattern (now relocated to `common/ai/` — see below), Feature 9/10's structured-output extraction idiom, and Feature 10's fail-open "vendor call, never block the underlying non-AI action" precedent.

**The shared transcription provider was relocated out of Feature 9's own folder into `common/ai/`, not duplicated.** `TranscriptionProviderInterface`/`OpenAiTranscriptionProvider` moved from `discovery/ai-search/` to `common/ai/`, behind a new `@Global()` `AiTranscriptionModule` (mirroring `AiEmbeddingModule`'s exact precedent and rationale) — both Feature 9's voice search and this feature's voice turns now share one Whisper client. Its timeout config was split out to its own `AI_TRANSCRIPTION_TIMEOUT_MS`, independent of `AI_SEARCH_TIMEOUT_MS` (which now scopes only Feature 9's extraction call) — a shared provider tied to one feature's env var name would have been confusing for the next reader.

**A second Nest module, not a second Multer config crammed into `ProfileModule`.** The voice-turn endpoint needs its own audio-size limit (`CONVERSATIONAL_SETUP_MAX_AUDIO_BYTES`), distinct from `ProfileModule`'s own `PROFILE_MAX_UPLOAD_BYTES` (photos) — since `MulterModule.registerAsync()` registers module-scoped defaults, not per-endpoint ones, the conversational-setup controller/service live in their own `ConversationalSetupModule` (importing `ProfileModule` for `ProfileService`), exactly mirroring how Feature 9's voice search sits in `DiscoveryModule` rather than `ProfileModule` for the same reason.

**Non-retention of the conversation is structural, not a retention policy.** There is no `ConversationTurn`/transcript table anywhere in the schema — `ConversationalSetupSessionStore` is the only place the turn-by-turn conversation ever exists, and it's a second, independent Redis connection to the same instance already backing the chat WebSocket pub/sub adapter (§5.3), under its own `conv-setup:` key prefix with a TTL refreshed on every turn. Deliberately not the pub/sub adapter's own client — a pub/sub-subscribed `redis` client has real usage restrictions, so mixing concerns there would have been fragile. Verified directly in the e2e suite, not assumed from the code's shape: a real session's Redis key is confirmed present mid-conversation and confirmed **gone** immediately after an explicit end call (`GET` against the raw key, not just "the API returned 200").

**The confirm endpoint is the only write path, and it is exactly `ProfileService.updateProfile()` — not a second, parallel one.** A new `source: 'FORM' | 'CONVERSATIONAL'` parameter (default `'FORM'`) was threaded through `updateProfile()`; every validation/age-check/moderation call inside it runs identically regardless of `source`. Verified for real, not just by code inspection: a confirmed `bio` that fails real content moderation returns 422 exactly like `PATCH /v1/profile` would, and a confirmed `birthDate` implying under-18 returns 400 exactly like FR-20 already requires.

**The highest-risk item — Persian/Gregorian calendar ambiguity for `birthDate` — is mitigated by always showing the calendar assumption, not just the resulting number.** The extraction schema's `birthDateDisplay` field is required to name both the interpreted source calendar and the resolved Gregorian date explicitly (e.g. `"شمسی ۱۳۷۰/۵/۱۲ → میلادی ۱۹۹۱/۰۷/۳۰"`), never the bare Gregorian date alone — verified directly in the e2e suite against a real extraction call, not just asserted from the prompt text.

**Which entry path actually completes a profile is now real, queryable data, not a guess.** `profile_completed` (already named in `product.md` §11, never previously instrumented) is the one event this feature wires up for real, via a new generic `AnalyticsEventProviderInterface`/`MockAnalyticsEventProvider` (persists to a real `AnalyticsEvent` row — a deliberate departure from the OTP/liveness mocks' log-only precedent, since the whole point is to let a real product decision be answered by querying real data later). Fires exactly once per user, from inside `ProfileService`'s existing completion check, carrying only `source` — never any actual profile field value. Verified directly: an e2e test completing a profile entirely through `PATCH /v1/profile` asserts a real `AnalyticsEvent` row with `source: 'FORM'`; a second test completing one through the conversational confirm endpoint asserts `source: 'CONVERSATIONAL'` — both read back from the real database, not asserted from the call site. `product.md` §11's remaining 17 events stay exactly as deferred as before this feature.

**The one real test-fidelity bug this feature's e2e suite caught was the same shape as Feature 9's**: the vendor-failure test's mock initially rejected with a bare `Error` instead of the `ServiceUnavailableException` the real `OpenAiConversationalExtractionProvider` actually throws — `withProfileFallbackHint` correctly left it alone (surfacing a real 500, not silently repackaging it as 503), so the bug was in the test's fidelity to the real failure shape, not in the fallback logic. Fixed by throwing the correct exception type in the mock. All ten `test/conversational-setup.e2e-spec.ts` tests, including the mandated real-Whisper-with-a-real-audio-file test (a fresh fixture, `test/fixtures/conversational-setup-name-city-fa.mp3`, generated via OpenAI TTS and round-tripped through real Whisper before being committed — same discipline as Feature 9's own fixture), pass cleanly and consistently against real OpenAI, real Neon, and real Redis — confirmed stable across three consecutive full clean runs.

**The same test-fidelity mistake had now independently recurred twice (Feature 9, then Feature 11) — reviewed after this feature shipped, and centralized rather than left to recur a third time.** `test/helpers/vendor-failure.ts` exports `rejectVendorUnavailable()`, the one place the real vendor-failure shape (`ServiceUnavailableException`, never a bare `Error`) lives for e2e tests to reuse — retrofitted into `ai-search.e2e-spec.ts`, `match-explanation-boost.e2e-spec.ts`, and `conversational-setup.e2e-spec.ts` in place of each file's own ad hoc version, plus the two unit-test spots with the same pattern (`ProfileService`/`MatchExplanationService` specs, using `ServiceUnavailableException` directly — a shared helper isn't warranted inside `src/` for a single-class import). Every future feature's vendor-failure test should reach for this helper rather than re-deriving the exception shape from memory.

### 5.9 Share My Date (Feature 12)

`backend/src/modules/date-share/` — the first feature in this codebase with a deliberately public, unauthenticated endpoint. No AI vendor is involved at all; the only external dependency is Feature 7's already-real S3-compatible presigned-URL mechanism, reused unchanged for the partner's photo.

**The public lookup lives in its own controller, not merged into the authenticated one.** `PublicDateShareController` (`GET /v1/date-share/:token`, no `@UseGuards`) is a separate file from `DateShareController` (`POST`/`GET`/`DELETE`, match-scoped, `JwtAuthGuard`) specifically so "this file has no auth guard" is visible at a glance rather than buried among guarded routes — the same reasoning `AuthController`'s bare style already established, now applied deliberately rather than incidentally.

**Two existing services are reused exactly, not reimplemented.** `ConversationAccessService.assertParticipant()`/`otherParticipant()` (Feature 4, newly exported from `ChatModule`) is the match-authorization check — 404 if the match doesn't exist, 403 if it exists but isn't the caller's, the codebase's own established shape for this kind of check (a deliberate departure from Feature 11's uniform-404 posture for its own *private, ephemeral* sessions — a `Match` is a durable, already-mutually-known resource, so there's no equivalent privacy reason to hide "this exists but isn't yours" behind a generic 404). `StorageProviderInterface.getUrl()` (Feature 7) serves the partner's photo through the exact same presigned, time-limited mechanism already built — confirmed in the e2e suite to still be freshly signed per call, not a stored copy.

**The share token gets the same security treatment as a refresh token, deliberately.** `CryptoService.hashShareToken()` mirrors `hashRefreshToken()`'s exact HMAC-with-a-dedicated-secret shape; the raw token (from `generateOpaqueToken()`, the same 32-byte/base64url primitive) is never persisted anywhere — confirmed directly in the e2e suite by fetching the real stored row and checking neither the `tokenHash` column nor the row's JSON serialization contains the raw token.

**A TTL anchored to a future business event, not to "now" — the first of its kind in this codebase.** `expiresAt = datetime + DATE_SHARE_LINK_BUFFER_HOURS` (24h, Open Items #2), computed from the date's own stated time rather than from `createdAt`. Every prior TTL in this project (OTP, refresh tokens, photo URLs, boost, conversational-setup sessions) counts forward from creation; a fixed "N hours from creation" TTL would have been actively wrong here — a date planned three days out could expire before it ever happens. Verified directly: a link created for a date four days out has an `expiresAt` far in the future, not a `createdAt`-relative one a naive implementation would produce.

**Failure-shape uniformity, verified byte-for-byte, not just "some 404 each."** A token that never existed, one whose link has expired, and one whose link was explicitly revoked all produce the identical RFC 7807 body (compared with `instance` excluded, since that field legitimately reflects the request path/token used and differs by construction — the fields that actually describe *why* the request failed are what must be identical). This also gave Feature 12 its own real test-fidelity lesson: the first draft of this comparison diffed the full body including `instance` and failed for a reason that had nothing to do with the feature — fixed by comparing only the meaningful fields, not by weakening what's actually being proven.

**A genuinely new abuse-resistance shape: per-IP rate limiting on an unauthenticated endpoint.** Every prior rate limit in this codebase gates a real, billed, or safety-relevant *authenticated* action; `DateShareLinkLookupAttempt` (mirroring `OtpRequest`'s existing per-IP axis, FR-4) exists purely to make token brute-forcing computationally infeasible, independent of any account. Verified for real — not just unit-tested, since this is exactly the kind of new boundary this project's standard requires testing live — via 101 concurrent real HTTP calls against the actual public endpoint, confirmed to trip 429. (Sequential calls were tried first and blew Jest's per-test timeout well before completing 101 round-trips to the real, remote Neon instance; switched to concurrent calls, which are also a more realistic simulation of the abuse pattern this limit defends against.)

**A real product decision, reversed once real testing exposed a wrong assumption: FR-156's "partner must be verified" check is otherwise unreachable under this project's own defaults.** The first e2e attempt at testing this used a normal (default `messagingPermission: VERIFIED_ONLY`) sharer against an unverified partner — and the match itself never formed at all (Feature 6's FR-79 messaging-permission gate silently blocks exactly this pairing upstream, at swipe time), so the test failed with a 404 (no match) rather than the expected 409 (unverified partner). Root-caused, not worked around: FR-156's check *is* real and *is* reachable, but only via a path that also requires the sharer's own `messagingPermission` to be `EVERYONE` — the test now sets that up explicitly rather than assuming default settings would ever reach this check. This also caught a second, independent test-authoring bug in the same investigation: single-digit phone-number suffixes across eleven e2e tests collided (more tests than available digits), so later tests silently inherited earlier tests' already-unverified/already-swiped user state — fixed with a monotonic per-test-run counter instead of hand-picked digits, the same class of fix Feature 9/10/11 have each needed once for their own phone/session-id schemes.

**A third real bug this suite caught before counting as done: a wrong endpoint guessed from memory, not verified.** `PATCH /v1/settings/privacy` (assumed by analogy with the feature's own name) doesn't exist — the real route, per `SettingsController`, is `PATCH /v1/users/me/privacy` (`@Controller('users/me')`). Caught by a real 404, the same category of mistake Feature 9's e2e suite caught once already for a different endpoint — fixed in both the test and the two `docs/requirements.md` references that had made the same wrong assumption.

**Follow-up after sign-off: the phone-number-collision mistake had now recurred often enough (Feature 9, 10, 11, this feature) to centralize, mirroring exactly how the vendor-failure-exception mistake was centralized after its own second recurrence (§5.8).** `test/helpers/unique-phone.ts` exports `uniquePhone()` — a module-scoped monotonic counter plus a per-run timestamp, guaranteeing a fresh, valid E.164 number on every call, both within one test file and across separate runs of the same file. Retrofitted into all eleven e2e spec files that previously hand-rolled a `+1XXX${suffix}N` scheme, replacing each file's own `suffix`/counter variables. One file, `auth-liveness.e2e-spec.ts`, had already independently named its own single-use local variable `uniquePhone` — the same underlying intuition (a name signaling the intent even before the generalized mechanism existed), just never generalized into something the other files could reach for. ### 5.10 Voice/Video Calling (Feature 13)

`backend/src/modules/calls/` — this feature never touches media at all (pure WebRTC, peer-to-peer or Cloudflare-TURN-relayed); the backend's only two jobs are minting short-lived TURN credentials and relaying opaque signaling payloads between two already-connected chat-gateway sockets.

**A genuine, sanctioned circular module dependency, resolved with `forwardRef()`, not designed around.** `ChatGateway`'s new `call:signal`/`call:hangup` handlers need `CallService` to validate a signal against real `CallSession`/block state; `CallService` needs `ChatGateway` back to push `call:incoming`/`call:limit-reached`. Rather than inventing a third shared module purely to avoid the cycle (which would have split `CallSession`'s own access-check logic away from the service that owns it, for no real benefit), `ChatModule` and `CallsModule` `forwardRef()` each other directly — the standard, Nest-sanctioned tool for exactly this shape of mutual need. Verified for real, not just type-checked: `tsc` alone cannot catch a circular-dependency wiring mistake (it would still compile), so the full `AppModule` was actually booted via `chat.e2e-spec.ts` before writing a single test for the new feature, confirming the DI graph resolves and the *existing* `message:new` push still works unregressed.

**Signaling rides the exact same namespace, room, and Redis-adapter infrastructure `message:new` already proved — deliberately not a second channel.** `ChatGateway` gained its first-ever client→server (`@SubscribeMessage`) handlers; every signaling payload (`call:signal`) is treated as opaque (never inspected, never assumed to be valid SDP/ICE) and is re-validated against real match/block state on *every single message*, not just once at call start — a call that was legitimate when it started but where one party got blocked mid-call must not be able to keep signaling.

**"Time-limited first calls" (`product.md` §7.3) means literally the first `CallSession` per match, not every call.** Determined by a simple existence check (`callSession.count({where:{matchId}}) === 0`) at start time — every later call for the same match is uncapped by design, not by omission.

**The server cannot force a real hangup, and this is documented as an architectural fact, not a gap left implicit.** Because media never routes through this backend, `call:limit-reached` (FR-192) is a **UX signal, not a security control** — it tells both clients a first-call's time limit has been reached, but two WebRTC peers already connected directly to each other could simply ignore it and keep talking. Actually enforcing the limit (ending the call, disabling call controls) is the responsibility of the client application this backend does not build — this backend's honest claim is "both clients are told from two independent sources," never "the call is forcibly cut." The nudge itself is a plain in-process `setTimeout` (`.unref()`'d, matching this codebase's existing fetch-timeout pattern), not a persisted or distributed job — an accepted simplification, since a missed nudge (a server restart, or a different instance than the one handling the call under horizontal scaling) only degrades a UX hint that was never a guarantee in the first place, never a security gap.

**A real, empirically-verified vendor integration before any code depended on it.** Cloudflare's real `generate-ice-servers` endpoint, real standing credentials, and the exact request/response shape were confirmed via a standalone probe (`POST .../credentials/generate-ice-servers`, real 201, real `iceServers` with `username`/`credential`) before `CloudflareTurnCredentialProvider` was written against it — the same discipline as every other real-vendor integration in this project (pgvector, Whisper, presigned S3 URLs). The credential TTL was revised once during review: the original 900s proposal (matching `PHOTO_URL_EXPIRY_SECONDS`) didn't account for non-first calls being uncapped and legitimately running past 15 minutes; corrected to a single, uniform 3600s TTL for every call rather than adding a second TTL code path.

**Two real client-reported fields, `connectionType`/`qualityStatsRef`, are explicitly untrusted by design** — the server has no way to independently verify what WebRTC connection path a call actually used (it never touches the media layer), so these exist purely for debugging call-quality complaints (`product.md` §8.4's own framing) and are never gated on for anything security- or billing-relevant.

All ten `test/calls.e2e-spec.ts` tests — including two real connected `socket.io-client`s exchanging a real signaling payload end-to-end through the real gateway + real Redis adapter, and a real Cloudflare TURN credential mint — pass against real infrastructure, confirmed stable across three consecutive full clean runs.

### 5.11 Shared `RedisService` — one connection owner, mirroring `PrismaService`

Until now, every Redis consumer opened its own connection independently: `ConversationalSetupSessionStore` (Feature 11) called `createClient()` in its own `onModuleInit`, and `RedisIoAdapter` (§5.3) did the same for its pub/sub pair, each with its own copy of the URL/error-handling logic. `backend/src/redis/redis.service.ts` (+ `redis.module.ts`, `@Global()`, registered once in `app.module.ts` next to `PrismaModule`) now owns the one general-purpose connection; `ConversationalSetupSessionStore` injects it and uses `.client` instead of managing its own lifecycle. `RedisIoAdapter` (not Nest-DI-managed itself — constructed manually in `main.ts` before `app.listen()`) fetches it via `app.get(RedisService)` and calls `.duplicateForPubSub()` for its pub client, then `.duplicate()`s that again for the sub client, matching the pre-existing pattern.

**What this does and does not fix — stated plainly, not implied.** This is a real code-quality/consistency win (one place owns the connection URL, TLS options, and error handling; a third future Redis consumer has somewhere obvious to plug into, matching this project's established "centralize after a second/third recurrence" practice already applied to `rejectVendorUnavailable()`/`uniquePhone()`). **It is not a fix for the third Watch item's Redis-connection-exhaustion hypothesis** (`docs/roadmap.md`), and was not expected to be: within a single app boot, `ConversationalSetupSessionStore` and `RedisIoAdapter` were already NestJS singletons (default provider scope), so each only ever opened one connection each regardless of this refactor. The Watch item's suspected exhaustion is driven by **15 independent e2e suites each booting their own separate `AppModule`** (plus `ai-search.e2e-spec.ts`'s one test that boots a *second* module instance to override the embedding provider) in one combined run — consolidating providers inside a single app instance doesn't change how many separate app instances a full regression run creates. Confirmed correct, not just designed: full backend unit suite re-run after this refactor — 44 suites, 358 tests, all passing, including the 20 tests directly covering the changed files (`redis.service.spec.ts`, the updated `conversational-setup-session.store.spec.ts`, `chat.gateway.spec.ts`).

Genuinely inherent, not a gap left by this refactor: pub/sub still needs two dedicated connections, never one — a subscribed `redis` v6 client has real usage restrictions and cannot also run general commands, so `duplicateForPubSub()` still opens a fresh connection rather than pretending to share a socket.

**Two real ordering bugs, both caught by actually running the affected e2e suites, not by `tsc`.** First pass: `RedisIoAdapter.connectToRedis()` now needs `RedisService.onModuleInit()` to have already run, but neither `NestFactory.create()` (production, `main.ts`) nor `moduleFixture.createNestApplication()` (the three e2e specs using `RedisIoAdapter`: `chat`, `report-block`, `calls`) trigger `onModuleInit` hooks by themselves — only `app.init()`/`app.listen()` do, and `connectToRedis()` was being called before either, in all four places. This would have broken production too, not just tests — it went unnoticed before this refactor only because the old code read `REDIS_URL` straight off `ConfigService`, which needs no init hook. Second pass, found while fixing the first: calling `app.init()` immediately after `createNestApplication()`/`NestFactory.create()` — before `enableVersioning()`/global pipes/filters were configured — bakes an *unversioned* route table into the app (`init()` is what runs `registerRouter()`), so every `/v1/...` request 404'd. **Fixed correctly, not patched around** — or so this section claimed at the time. **This was wrong, corrected during Feature 17 (2026-08-24), and the correction is worth stating plainly rather than quietly editing away.** The order described above — `app.init()` *before* `RedisIoAdapter` construction/`useWebSocketAdapter()` — is exactly backwards. `app.init()` is what binds every `@WebSocketGateway` to whichever adapter is active *at that moment*; calling `useWebSocketAdapter()` afterward is a real, silent no-op for gateways already bound, confirmed directly by Nest's own runtime warning ("useWebSocketAdapter() was called after WebSocket gateways were already initialized... will NOT be applied to existing gateways") once something finally looked for it. The "confirmed by reading `nest-application.js` directly" claim above was real reading, but of the wrong code path: `app.listen()`'s own re-init *is* correctly idempotent (that part was verified accurately), but that idempotency is irrelevant to the actual bug — gateway-to-adapter binding happens once, inside `init()`, and is never redone by the later `listen()` call regardless of the adapter set in between. The result: `RedisIoAdapter` was constructed, connected to real Redis, and handed to `useWebSocketAdapter()` in every one of these code paths — and every single one of those steps was silently discarded, in production and in all three e2e suites (`chat`, `calls`, `report-block`), from this exact "fix" through Feature 17. See §5.3's own historical correction for why nothing caught it (a single-process test structurally cannot distinguish a correctly-wired Redis adapter from Nest's plain in-memory default), and Feature 17's real, genuinely-verifying fix: the adapter is now set *before* `app.init()` everywhere (`main.ts` and all three e2e specs), which in turn required decoupling `RedisIoAdapter.connectToRedis()` from `RedisService`'s own DI-managed connection (only available *after* `app.init()`'s lifecycle sweep runs `onModuleInit` hooks — the very dependency this fix needed to stop having). `RedisIoAdapter` now opens two direct, independent `redis` v6 connections of its own instead of borrowing `RedisService`'s. The "verified stable across two consecutive clean runs" claim in the sentence this replaces was true on its own terms (the suites *did* pass, twice) — it just wasn't evidence of the thing it was cited for, which is the actual lesson worth keeping: a green single-process e2e run is not evidence that a multi-instance pub/sub mechanism works, no matter how many times it's repeated.

### 5.12 Frontend shell, auth, and login (Feature 14) — the first frontend feature

`frontend/` (Next.js 16, App Router, TypeScript, Tailwind, shadcn/ui, React Query, Zustand, Framer Motion, Playwright) — bootstrapped, not scaffolded-and-abandoned: real design tokens from `docs/design-system.md` wired into Tailwind's `@theme`, a real login/liveness flow against the real backend, real Playwright coverage.

**Next.js 16 has real breaking changes from what a general LLM's training data assumes — read first, not assumed.** The project's own `frontend/AGENTS.md` (regenerated by `next dev` itself) warns of this explicitly and points at `node_modules/next/dist/docs/`. **A real client-side gap found by writing the actual failure-mode test, not just the happy path**: the first version of `AuthRehydrator` (`components/providers/app-providers.tsx`) cleared the in-memory session on a failed rehydration but never actually navigated anywhere — meaning a protected page whose httpOnly cookie had gone invalid (revoked, expired) would sit there silently instead of returning the user to `/login`. `proxy.ts`'s edge gate only checks the cookie's *presence* (FR-211, deliberately not a security boundary), so it lets such a request through; nothing else was catching the invalid-cookie case until this was noticed while designing exactly that test. Verified against a real corrupted cookie value (not just an absent one — `context.addCookies()` with a garbage token), confirmed to redirect for real.

**Two real, pre-existing bugs found and fixed while verifying this feature — neither caused by it, both real, both now fixed.**

1. **A genuine SQL-parameter-binding defect in Feature 9's ranked-cursor pagination, latent since that feature shipped, exposed for the first time here.** `AiSearchService`'s "un-embedded candidates sort last" test started failing — confirmed by direct isolation, not assumed, to be a real bug, not the already-documented "heavy load" flakiness pattern. ## 6. Safe Update Policy — no destructive migrations, no breaking API changes

A hard rule, not a guideline: **a database migration must never destroy or silently reinterpret existing user data, and an API change must never break a client that hasn't updated yet.**

- **No migration drops a column or table, or changes what an existing column means, without a deprecation period first**: stop writing to the old shape, backfill/dual-write if needed, let a full release cycle pass (longer if mobile clients are in the field — see below), then remove it. "Nothing reads this anymore" is not sufficient justification for removing it in the same release that stops using it.
- **No in-place rename** of a column/table that changes the read/write contract for a client that hasn't updated. Add the new name, migrate reads/writes onto it, retire the old one later — not in the same step.
- **API changes preserve backward compatibility for existing clients.** `/v1` URI versioning is already in place (`product.md` §8.2) specifically for this reason: an actually-breaking change gets a `/v2` (or a genuinely new endpoint), not a modification of `/v1` that changes what existing clients receive. Adding a field to a response is safe; removing one, renaming one, or changing its type/meaning is not.
- **Why this matters more than the generic "be careful with migrations" instinct**: mobile app users do not update on the server's release schedule. A user running an old build against a server that already assumes the new data/API shape is an ordinary, ongoing scenario for this product, not a hypothetical edge case — and a migration or API change that isn't safe for that user directly threatens their profile, messages, or settings. That's the exact failure this policy exists to prevent.
- **Applies going forward to every migration**, including how the ones already written for Features 1–3 should be read: everything so far has been additive (new tables, new nullable columns) — nothing has needed a destructive or meaning-changing edit yet, so this policy hasn't actually been tested against a real conflict. The first migration that needs to remove or reshape something that already exists is the first real test of it — treat that as a deliberate dual-write/backfill/deprecate design decision, not a quick schema edit.
