    1. **`ChatGateway`'s Socket.IO transport had no CORS configuration at all**, silently blocking every cross-origin browser connection (`main.ts`'s `app.enableCors()` only covers the Express/HTTP layer, not Socket.IO's own separate engine.io CORS check) — confirmed via a real browser CORS console error, fixed by configuring `cors` centrally in `RedisIoAdapter.createIOServer()`.

Silently correct-by-coincidence on the one dev instance that's ever run (same-process delivery works identically either way), which is exactly why nothing caught it before. The new test boots two independent app instances on two real ports and proves delivery from one to the other, the only path being the real Redis channel. Verified as a genuine, sensitive guard, not just a passing test: the exact original bug was deliberately reintroduced, the suite re-run, and the new test failed with a real 30s timeout while the file's three single-instance tests kept passing — then reverted and reconfirmed clean.

JSON.parse(text) : undefined` resolved that to `undefined`, which React Query explicitly forbids as query data. Not a Feature 17 regression — this feature's e2e suite's own test script just happened to trigger it via an unnecessary extra `page.reload()`, which was removed (the real assertion doesn't need a full reload, a plain SPA navigation already re-fetches). Tracked below as a real, still-open architectural gap, matching this project's own precedent of accepting this exact risk category rather than building a deeper server-side fix (e.g. a rotation grace period) speculatively.

    **The one real, structural risk this feature introduced, scoped and guarded deliberately.** Two existing gates — `proxy.ts` (redirects any cookie-less request to `/login`) and `AuthRehydrator` (force-redirects on failed rehydration for any non-`/login` route) — had never had a second legitimate exception before. A real, considered risk caught and designed around *before* being caught by a test: a first draft of the `AuthRehydrator` exemption copied `/login`'s own unconditional `clearSession()` call, which would have silently destroyed an already-authenticated user's real in-memory session on nothing more than an in-app navigation to their own share link — fixed by only clearing state when a fresh tab's status is genuinely `"unknown"`, leaving an already-real session untouched; `/login`'s own existing, already-shipped behavior was deliberately left unchanged, since `proxy.ts` already structurally guarantees no authenticated visitor can ever reach it.

    **Revoke's isolation from the newly-public route, confirmed directly on explicit user follow-up, not assumed.** `app/date/` is the only route in the app under that prefix (confirmed by a direct search — the `/date/` exemption's blast radius is exactly the one public page, nothing else); revoke's own UI (`DateShareSheet`) is only ever rendered inside the authenticated `/matches/:matchId` route, never inside the public page's own component tree; the two hit entirely different backend endpoints (`DELETE /v1/discovery/matches/:matchId/date-share/:linkId` vs. `GET /v1/date-share/:token`); and `lib/queries/date-share.ts`'s `revokeDateShareLink()` (via the shared, session-aware `apiFetch`) and `getPublicDateShare()` (via its own dedicated, deliberately auth-header-free fetch) share no call path despite living in the same file. `proxy.ts`'s exemption is Next.js page-navigation middleware only — it has no bearing on backend API calls at all.

## HNSW index on `users.bioEmbedding` — real bug found and fixed (2026-09-18, follow-up)

User directly questioned whether the audit's "HNSW not used" finding (§2.4-adjacent) was genuine small-dev-table planner behavior (seq scan legitimately cheaper than an ANN index on ~300 rows) or a real configuration bug, and asked for a definitive empirical answer, not an inference.

**Root cause, confirmed directly against the live dev DB, not assumed:**
```sql
SELECT indexname FROM pg_indexes WHERE tablename = 'users';
-- returned: users_createdAt_id_idx, users_livenessStatus_idx, users_phoneHash_key, users_pkey
-- zero HNSW indexes. The index did not exist at all.
```
This was **never** a planner-choice-on-small-data question — there was no index for the planner to choose. Traced via migration history: `20260820115133_add_ai_search/migration.sql` created `users_bioEmbedding_hnsw_idx` (`USING hnsw ("bioEmbedding" vector_cosine_ops)`). Because Prisma's diff engine can't see a hand-written raw-SQL index on an `Unsupported("vector(1536)")` column, every `prisma migrate dev` run since has proposed dropping it — and every migration between `20260820192411` and `20260823180000` explicitly strips that auto-generated `DROP INDEX` with a `NOTE` comment so it survives. **`20260903134429_feature_24_profile_depth_who_liked_me` is the one migration that missed this step** — its `DROP INDEX "users_bioEmbedding_hnsw_idx";` (line 23) went through for real, and no migration since recreated it. A genuine ~2-week-old regression, invisible because nothing failed loudly — bio-embedding ranking queries still returned correct results, just via seq scan instead of ANN, on a table small enough that no one noticed the missing index.

**Fix**: new migration `20260918193000_restore_bioembedding_hnsw_index` recreates the exact original index definition, with a NOTE for the next `prisma migrate dev` run to strip the auto-proposed drop again (same pattern as before). Applied via `prisma migrate deploy` — succeeded (Postgres would have failed the whole `migrate deploy` run immediately had the `CREATE INDEX ... USING hnsw` statement errored, e.g. missing `vector_cosine_ops` support, so success is direct confirmation the index now exists, not an assumption).

**Follow-up test executed 2026-09-20, against the dedicated load-test Neon branch** (`backend/scripts/load-test/.env.load-test.local` — never the shared dev DB, per this project's own established load-testing discipline, `docs/load-testing.md` Decision §3). 20,000 synthetic rows with real random 1536-dim embeddings were inserted (523 → 20,523 rows), `ANALYZE users` run, both query shapes captured with real `EXPLAIN (ANALYZE, BUFFERS)`, then all synthetic rows deleted and the count verified back to exactly 523 — zero permanent footprint.

**Definitive result: the restored index is necessary but not sufficient — the app's actual query shape does not use it.**
- **(A) Real `ai-search.service.ts` shape** (`WHERE id = ANY(2000 ids)` CTE, then `ORDER BY distance LIMIT 20`): `Bitmap Heap Scan` on `users` via `Bitmap Index Scan` on `users_pkey`, then a `Sort (top-N heapsort)`. **HNSW index not used at all.** Execution time: **71.9ms**.
- **(B) Bare unfiltered top-K** (`ORDER BY bioEmbedding <=> vec LIMIT 20`, no `id = ANY` pre-filter): `Index Scan using "users_bioEmbedding_hnsw_idx"`. Execution time: **6.0ms** — **~12x faster**.

This confirms the original audit's structural inference (§2.4) exactly, now with real numbers instead of a guess: pgvector's HNSW `ORDER BY ... LIMIT` acceleration only applies when the index scan itself can drive the ordering. Once the query pre-filters to an arbitrary primary-key `id = ANY(...)` set first (as the real deck/discovery pre-filter does, capped at 2000 candidates), Postgres correctly chooses to fetch those specific rows directly by primary key and sort in memory — a bitmap scan over ≤2000 known ids is cheaper than an ANN index traversal, and there is no way for the index to "know" in advance which rows will pass an arbitrary id list. **This is not a bug** — it is the correct, cost-based choice for this query shape — but it does mean the HNSW index currently provides **zero benefit** to the actual AI-search feature as built, regardless of table size, since the candidate pool is capped at 2000 either way. Restoring the index was still the right fix (some other future query could rely on it, and the audit's original "PARTIAL — configured but likely unused" status is now correctly "confirmed unused for the current query, working as designed elsewhere"), but closing this fully would require restructuring the ranking query itself (e.g., a hard cutoff distance plus a true `ORDER BY <=> LIMIT` index-driven scan, filtered afterward, rather than pre-filtering by id first) — flagged as a real, open follow-up, not attempted in this pass since it changes ranking semantics and needs a product decision, not just an index fix.

Cleanup verified directly, not assumed: final row count after deletion (523) matched the pre-test baseline (523) exactly.

## Dev machine memory pressure — the likely real root cause behind this session's recurring server outages

**A systemic finding, not a footnote on one feature.** Across this project's history, "MinIO/clamd died again" (and, once, the backend and frontend dying too) has repeatedly been treated as a series of independent, unexplained incidents — each one individually root-caused ("was it credential drift? no, it just wasn't running") and fixed by restarting the specific dead service, without ever asking *why* local dev-only services keep dying on their own with no crash log and no clear trigger. Found while adding Feature 24's own frontend e2e coverage (a long session running the app plus its own multi-context Playwright suites): this dev machine has a real, measured, and quite tight memory budget, and it is very plausibly the actual common cause behind most (not necessarily all) of these prior "died again" incidents.

**Measured, not assumed:**
- Total physical memory: **~7.88GB** (`Get-CimInstance Win32_OperatingSystem`, `TotalVisibleMemorySize`) — a genuinely small budget for this project's real stack (a NestJS backend, a Next.js/Turbopack frontend, MinIO, ClamAV, plus this coding agent's own process) running concurrently.
- Free memory was directly checked at three separate points during one session: **2.14GB free**, then later **1.55GB free**, then, immediately after the full stack (backend, frontend, MinIO, `clamd`) was found to have crashed with zero warning mid-session, **1.55GB free** again — the crash itself did not free meaningful memory, meaning the system was already deep in the danger zone before the crash, not tipped over by one single large spike.
- A real, direct process-memory snapshot (`Get-Process | Sort-Object WorkingSet -Descending`) at one such low-memory moment showed the largest consumers were **not** this project's own dev services: the user's own Chrome browser (13 separate `chrome.exe` processes under one parent — Chrome's normal multi-process architecture, but summing well over 1GB across them), this coding agent's own two processes (~390MB + ~275MB), Windows Defender's `MsMpEng` (~212MB), a second, separate antivirus engine `ekrn` (ESET, ~131MB — running *alongside* Windows Defender, not instead of it), Telegram (~129MB), and Windows Search's own `msedgewebview2` helper processes. This project's actual dev stack (backend, frontend/node, MinIO) each individually measured in the 130-260MB range — real, but smaller than several of the unrelated background processes above.

**What this explains:** every prior "local dev-only dependencies don't survive a machine/session restart" incident logged under "Known infrastructure debt" above (MinIO, twice; `clamd`, alongside it) is consistent with this same underlying cause — a long-running session's cumulative memory footprint (browser testing, multiple real Playwright Chromium contexts, a long-lived Node dev-server process's own growth) eventually crosses whatever the OS's real available headroom is, and something gets silently killed. This was never confirmed as the definitive cause of every past incident (no memory reading was taken at the time), but it is now a real, concrete, measured explanation worth checking first, rather than re-diagnosing each fresh occurrence as if it were a novel mystery.

**Practical recommendations, in order of effort:**
1. **Free, immediate, no config change:** before a long dev/testing session, close applications with no relation to this project that are already consuming real memory — the user's own Chrome browser (if not actively needed for something else) and Telegram together were measured at well over 1GB combined in the snapshot above. This alone may be enough headroom for a normal session.
2. **Worth asking about, not assumed intentional:** running both Windows Defender (`MsMpEng`) and a separate third-party antivirus (`ekrn`/ESET) simultaneously is unusual — normally one is set to passive/disabled mode when a second, dedicated AV product is installed, since real-time-scanning two engines at once doubles that overhead for no real security benefit. Worth checking Windows Security settings for whether Defender is meant to be in passive mode here.
3. **Test-running discipline (already adopted this session):** run e2e suites with `--workers=1` rather than default parallelism, and avoid running the backend and frontend e2e suites concurrently — each real browser context is a full separate Chromium process, and this session directly observed resource-contention-driven test flakiness (different, changing subsets of tests failing across repeated full-suite runs, each failure passing cleanly in isolation) that disappeared once suites were run one at a time. **Do not run multiple heavy Playwright test-suite processes in parallel on this machine, even as separate background invocations — run them sequentially.** Confirmed with a real incident, not a guess: two separate `npx playwright test` background processes launched at the same time (one running `welcome-tour`/`profile`, one running `discovery`) drove the backend to a real, unhandled crash (`Error: read ECONNRESET` on an in-flight Redis/WS stream, an uncaught promise rejection that took the whole Node process down — not a graceful 429/500) — every test in both suites failed until the backend was manually restarted. Running the exact same suites one after another, never concurrently, has been clean all session.
4. **Related, separately confirmed this same session: this environment does not keep a detached process (`Start-Process`, or an OS-level background `&`) alive once the shell call that launched it returns** — only a process started via the tooling's own persistent background-tracking mechanism survives across calls. A dev-stack orchestrator script that uses `Start-Process` for clamd/MinIO/backend/frontend will report success but leave every service dead the moment its own invocation ends; each of the 4 services must instead be started as its own separately-tracked background command.
5. **Structural, if this keeps recurring:** this machine's ~8GB total is genuinely tight for this project's real local stack plus real e2e testing running at the same time. If outages keep recurring even after 1-3 above, the real fix is more memory (if this is a VM/cloud instance, a larger size is a direct, low-effort option) rather than continuing to treat each outage as a fresh incident to diagnose.

**Operational rule going forward:** before assuming a dead local service is a code regression or a fresh mystery, check free memory directly (`Get-CimInstance Win32_OperatingSystem`) — sub-2GB free is a real, recurring condition on this machine, not a hypothetical, and explains the symptom far more often than a genuine application bug does.

## Dev database hygiene — a recurring, expected characteristic, not a one-off finding

**This project's own standing testing philosophy — every e2e suite (backend and frontend alike) runs against the real, persistent main dev database, never a mock or a throwaway test DB — has one direct, permanent consequence: the main dev database accumulates real, permanent test users every time any e2e suite runs.** This is not a bug, not a misconfigured test target, and not a one-off accident to be re-investigated and re-alarmed-about each time it's noticed. *Investigation before any fix, per explicit user request*: (1) `checkGrounded()` is a second, fully independent `gpt-4o-mini` call — free-text profile facts and free-text claims in, a holistic natural-language judgment out, constrained only by the *output shape* (OpenAI Structured Outputs), never the reasoning process. (3) A fully deterministic replacement isn't feasible for the *positive* case (genuine semantic paraphrase, e.g. "کوهنوردی" + "طبیعت‌گردی" → "shared love of nature," requires real semantic understanding — the whole reason an LLM is used at all) — but every fabricated claim tested shared one concrete, mechanically-checkable shape: a specific, nameable fact (a place, an event, a relationship, a physical detail) with zero textual basis anywhere in either profile. That shape is exactly what a deterministic second layer can catch reliably, without needing to judge "reasonableness" at all.

*Step 1 — prompt fix, with an honest negative result along the way.* First attempt: `temperature: 0` + 8 few-shot "NOT-grounded" examples (the exact fabrications from this session's own probes). Real, isolated re-probe of the same 8 cases: **3/8 — worse than the 5/8 baseline**, not better. *Step 2 — the deterministic entity-veto layer, built independent of step 1's result, per explicit instruction.* New `grounding-entity-check.ts` (pure, unit-testable, no OpenAI dependency): given a list of extracted "specific fact" strings, a claim is only rejected if *every one* of its named entities has zero substring match anywhere in either profile's real, raw text (bio, interests, city, displayName, dating intent) — deliberately asymmetric: this layer can only make an already-GROUNDED verdict *stricter*, never loosen a real rejection, so it never fights the LLM-judge's own paraphrase calls. Wired into `checkGrounded()` as a second opinion that only runs when the LLM-judge says GROUNDED: a new `extractEntities()` call (same model, `temperature: 0`, a much narrower "list the specific things this claim names" extraction task) feeds `hasTextualSupport()`, and an entity with no textual basis overrides the verdict to `grounded: false`.

## Real, serious safety gap: no mechanism ties profile photos to the identity that passed liveness

**Confirmed by directly reading the code, not assumed — there is currently zero face-matching or identity-binding of any kind between liveness verification and profile photos, anywhere in this codebase.** Found while investigating an unrelated Feature 26 follow-up, but real and significant enough to warrant its own top-level tracking entry rather than being buried under that feature.

**What actually exists today:**
- `LivenessSession` (`backend/prisma/schema.prisma:629-641`) stores only `status` (pending/pass/fail) and an opaque provider session reference — no image, no face embedding/descriptor, nothing biometric that could ever be compared against anything later. This is by explicit design: `liveness-provider.interface.ts`'s own doc comment states the interface "must stay result-only... and must never be extended to accept or return raw capture frames, per the zero-retention requirement in `product.md` §5."
- On a liveness pass, the only side effect anywhere in the codebase is `User.livenessStatus = true` (`backend/src/modules/verification/verification.service.ts:115-119`) — a single boolean, set once, and (confirmed by searching every write site in `backend/src`) never set back to `false` by any application code path, ever.
- Profile photo upload (`backend/src/modules/profile/profile.service.ts:390-452`) runs exactly three checks: malware scan (ClamAV), format re-encode (WebP + EXIF strip), and OpenAI content moderation (NSFW/inappropriate-content classification). **None of these three checks has anything to do with identity** — there is no face-comparison library, no embedding-similarity check, and no call anywhere in the photo-upload path to the one embedding provider this codebase does have (`EmbeddingProviderInterface`), which exists exclusively for bio-text semantic search, never images.
- The "verified" badge shown to every other user — on the discovery card, matches, chat, AI search results, and Share My Date — is a direct, unconditional passthrough of this same `livenessStatus` boolean at every call site (`deck.service.ts:216`, `who-liked-me.service.ts:92`, `match.service.ts:89`, `conversation.service.ts:71`, `ai-search.service.ts:179`).

**The real, concrete consequence:** a user passes liveness once — trivial today, since the only wired provider (`MockLivenessProvider`) auto-passes every session with zero real biometric checking — and the "verified" badge (plus every verified-only discovery/messaging gate that reads the same field) stays true **forever**, completely independent of what photo(s) that user uploads, replaces, or has ever uploaded. Nothing anywhere detects or prevents a user from passing liveness once and then uploading someone else's photo as their profile picture. This is a genuine catfishing/impersonation vector that the "verified" badge's own implied meaning to end users (this account belongs to a real, live human matching what you see) does not actually hold once a real, non-mock liveness vendor is wired in — the badge would still only ever mean "passed a liveness check at some point," never "the photos you're looking at are this same verified person."

**Not caused by, and not scoped to fix in, any feature that has shipped so far** — flagged here as a standing, real, open risk. No code fix has been written for this; per explicit user instruction this is documentation only for now. See `docs/legal-checklist.md` Part B for the corresponding legal-review flag — this is not purely an engineering backlog item, since any eventual face-matching fix would itself constitute a new, distinct form of biometric special-category-data processing under GDPR Article 9, requiring its own legal sign-off before being built, not just before being turned on.

- **Current state:** `ContentModerationProviderInterface` (`backend/src/common/moderation/content-moderation-provider.interface.ts`, unchanged) is implemented by `OpenAiContentModerationProvider` (`backend/src/common/moderation/openai-content-moderation.provider.ts`), calling OpenAI's Moderation API (`omni-moderation-latest`, one model for both text and image) directly via `fetch` — no SDK dependency. `MockContentModerationProvider` (the old mock) was deleted, not left dead in the tree, matching the precedent from malware scanning and storage.
- **Fails closed** (mirroring `ClamAvMalwareScanProvider`'s exact pattern): a network error, timeout, non-2xx response, or unparseable body throws `ServiceUnavailableException` (503) rather than treating unscanned content as approved.
- **The human review queue is a new `ModerationFlag` model + admin surface**, not just a vendor swap — this was the harder half of the feature. Rejected content was previously never persisted anywhere (the 422 response and an audit-log line were the only trace), so there was nothing for a review queue to show; every rejection now retains the actual content (bio/message text directly; a flagged photo's already-processed bytes quarantined under a `flagged/` prefix in the same `STORAGE_PROVIDER` bucket Feature 7 built) so a human can actually evaluate the vendor's decision. `GET`/`PATCH /v1/admin/moderation-flags` reuses Feature 5's exact `AdminGuard`/cursor-pagination/resolve pattern, not a new design. Resolving a flag (`UPHELD`/`OVERTURNED`) is a record only — it does not republish the content, the same "review ≠ enforcement" posture Feature 5 established for report resolution.
- **Verified working end-to-end against the real OpenAI API**, not a mock — confirmed directly before building anything further: a first smoke test hit a persistent `429` on `/v1/moderations` specifically (while `/v1/models` worked fine with the same key), traced to the project's billing not yet being active; once billing was enabled, both a benign and a genuinely threatening test string were correctly classified, and a real 64×64 WebP image round-tripped successfully (a degenerate 1×1 test pixel first triggered a real `500` from OpenAI's side — not a bug, just an unrealistic input no real upload would ever produce). `test/moderation.e2e-spec.ts` exercises the real vendor for text rejection end-to-end (bio and chat message, both genuinely flagged, both retained as `ModerationFlag` rows, both reviewable through the real admin endpoints) and substitutes a deterministic provider only for the photo-quarantine and fail-closed tests specifically, since reliably forcing a real vision classifier to flag a synthetic test image isn't practical and, for the nudity/violence categories, isn't an appropriate thing to embed as a test fixture — the quarantine write itself still goes through real MinIO.
- **A real diagnostic detour worth remembering:** partway through this verification, both `clamd` and MinIO turned out to have stopped running (enough real time had passed since they were started earlier in the same session) — every moderated-photo-upload request failed closed with a 503 regardless of the moderation logic itself, which briefly looked like a Feature 8 regression until `curl`/`netstat` confirmed neither dependency was actually listening. Both are manually-started local dev processes with no supervisor to restart them; noted here so the same red herring doesn't cost time again (see the Production Readiness Checklist's "Tracked, but not enforced" list).
- **Deployment note:** `OPENAI_API_KEY`/`MODERATION_TIMEOUT_MS` are the only env vars involved — same "swap via config, not code" pattern as every other vendor in this file. No EU-region equivalent concern applies here the way it does for Storage (OpenAI's moderation endpoint isn't a data-residency-sensitive store of user content beyond the `ModerationFlag` table this app already controls).

## Locked-in technical decisions (recorded, not re-litigated)

- ORM/migrations: **Prisma Migrate + Prisma Client** (over TypeORM) — decided for type-safety and migration DX.
- Backend framework: NestJS (per `product.md` §8.2).
- Database: PostgreSQL (per `product.md` §8.3).
- OTP code hashing: **bcrypt** (via `bcryptjs`, a pure-JS implementation — chosen over native `bcrypt`/`argon2` bindings to avoid a native-compile step on Windows dev machines without build tools). Phone numbers and refresh tokens stay on keyed HMAC-SHA256, since both need a deterministic hash for an indexed DB lookup, which bcrypt's per-call random salt does not support — see the comment in `backend/src/common/crypto/crypto.service.ts`.
- `AuditLog` (product.md §9) implemented from this first feature onward: `backend/src/common/audit-log/audit-log.service.ts`, a global provider. Currently recorded events: `OTP_VERIFY_FAILED`, `BIOMETRIC_CONSENT_ACCEPTED`, `LIVENESS_VERIFICATION_PASSED`/`LIVENESS_VERIFICATION_FAILED`. Extend this list as new security-relevant actions are added in later features rather than starting a parallel logging mechanism.

See `docs/architecture.md` for the system-level view (module structure, the provider-abstraction pattern behind every mock in this file, and operational notes on external runtime dependencies like `clamd`).
