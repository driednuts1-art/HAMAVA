## 1. Method

Full-codebase search (`frontend/app`, `frontend/components`, `frontend/lib`, `backend/src`) for hardcoded Persian/Arabic-script text and for RTL-dependent code (`dir=`, physical-direction Tailwind utilities, `flex-row-reverse`, icon-mirroring transforms, the Vazirmatn font, the girih pattern). Every hit was checked, not just counted — comment-only matches and false positives (e.g. `rounded-lg`, which matched a naive "left/right" search but rounds all four corners) are called out explicitly below rather than folded into the totals.

## 2. Key structural finding: **no i18n layer exists**

There is no `frontend/lib/i18n`, `frontend/messages/`, `frontend/locales/`, or any translation dictionary file anywhere in the codebase. Every Persian string is inlined directly as a literal in the component/page that uses it. **This is the single biggest driver of the effort estimate in §4** — this isn't "swap one dictionary file," it's "find and rewrite ~550 individual string literals scattered across 64 files," and doing that without first introducing a real i18n layer would just recreate the same scattered-string problem in a different language, permanently blocking any future second language.

This is a real, structural simplification for the migration: there's no "undo a systematic RTL abstraction," just direct, file-by-file fixes.

**Total: ~19 files touch RTL-dependent code, of which only ~11–13 individual style occurrences are genuine must-fix items.**

### 3.3 A finding beyond what was asked, surfaced because it's real and easy to miss: the Jalali calendar

`lib/jalali.ts`, `profile/birth-date-field.tsx`, and `date-share/date-time-field.tsx` implement the **Persian/Solar Hijri (Jalali) calendar**, not just Persian month-name *labels* on a Gregorian calendar — the birth-date and date-share pickers are built around Jalali year/month/day entry and conversion. For a genuinely global, English-first product, this is very likely a Gregorian-calendar UI, not a Jalali UI with translated month names — that's a real UI/interaction redesign (a different picker shape, different validation, different conversion logic to whatever the backend actually stores), not a string swap. **This needs its own scoping pass before Phase 2 estimates it precisely** — this audit did not verify whether `User.birthDate` is stored as a plain Gregorian timestamp already (likely, since Prisma's `DateTime` doesn't care about calendar systems) with only the *display/input* layer being Jalali, which would make this a frontend-only, reasonably contained change — but that should be confirmed, not assumed, before committing to a scope number.

### 3.4 Seed data

`docs/test-users.md` documents **20 curated, real, live dev-DB users** with Persian names/cities (علی رضایی/تهران, etc.), created via `backend/scripts/seed-test-users.ts` (80 Persian occurrences: names, cities, bios, prompt answers). A second script, `seed-bulk-users.ts` (150 Persian occurrences, name/city/bio-template pools for 100 additional bulk-volume-test users), mostly failed on its last real run (0/1, moderation-service 429s) — so only the 20 curated users are actually live today. `backfill-seed-prompts.ts` (60 occurrences) and `clean-non-seed-users.ts` (20 occurrences — a hardcoded list of the 20 seed names, used to identify and protect/clean seed data during other test runs) also carry Persian data. No `backend/prisma/seed.ts` exists — all seeding goes through the real API, not a DB-level fixture load.

## 4. Effort estimate

Broken into tiers by what kind of work each is, since they carry genuinely different risk profiles and don't all belong in the same estimate bucket:

| Tier | What | Real size | Risk profile |
|---|---|---|---|
| **1 — Foundation** | Introduce a real i18n/dictionary layer (currently doesn't exist), flip `dir`/`lang`, swap font, remove/replace the girih background | Small file count (~5–6 files), but **must land as one atomic change** — a page can't be half-RTL/half-LTR without looking broken mid-migration | Low technical risk, high "must not ship partially" risk |
| **2 — String translation** | Rewrite ~547 Persian string occurrences across 64 frontend files into the new i18n layer | The largest single line-item by file count and occurrence count | Low-medium — mostly mechanical, but enum-backed strings (gender, education, report-reason, language) need care to translate the *display label* without touching the *stored value* the backend expects |
| **3 — RTL/layout flip** | Fix the ~11–13 genuine physical-direction Tailwind occurrences across 13 files | Small — meaningfully smaller than Tier 2 | Low — mostly mechanical, a few (match-moment composition) need a real design look, not just a class swap |
| **4 — Calendar redesign** | Jalali→Gregorian date picker (birth date, date-share) | Unknown until scoped (§3.3) — plausibly small if storage is already Gregorian, plausibly a real interaction redesign if not | Medium — the one item this audit could not fully bound |
| **5 — Backend LLM content** | Redirect 2 LLM system prompts from Persian to English output, translate 5 production files' static strings (greetings, 10 profile prompts, language-enum labels) | Small file count (7 files) | Medium — LLM-output language changes need real re-verification (does the model actually respond in English reliably?), not just a string diff, similar in kind to this project's own past grounding-check verification work |
| **6 — Seed data** (blocked on §5.1's decision) | Re-seed or leave as-is, across 4 backend scripts + 2 docs | Small once decided | Low technical risk, but check first whether any e2e spec hardcodes a specific seed name/phone — not verified in this pass |

**Honest bottom line**: this is not a single small feature. Tiers 1–3 alone touch on the order of 70–80 distinct files once de-duplicated (heavy overlap between List A and List B — e.g. `safety-sheet.tsx` appears in both). It is also not one undifferentiated giant project — the tiers above have real, natural seams. **Recommended sequencing, matching this project's own existing feature-by-feature discipline** rather than inventing a new process:

1. Brand-name decision first (design-system-v2.md §7 #1) — the foundation tier (Tier 1) bakes the final name into `<title>`/metadata/font choice, so doing Tier 1 twice because the name changed later is real, avoidable rework.
2. Tier 1 (foundation) as its own atomic PR/feature — nothing else can safely land before this.
3. Tier 2, sliced by the same feature-area groupings §3.1 already fell into naturally (Auth → Profile → Discovery → Settings → Chat/Calls → Matches/misc) — each is independently shippable behind Tier 1, matching how every other feature in this project has been scoped and reviewed one at a time.
4. Tier 3 folded into each Tier-2 slice as it's touched (fixing a component's RTL classes while its strings are already being rewritten is less total work than two separate passes over the same file).
5. Tier 4 (calendar) scoped precisely, then executed — likely lands alongside the Profile slice of Tier 2, since `birth-date-field.tsx` is a profile component.
6. Tier 5 (backend LLM content) — fully independent of frontend work, can run in parallel.
7. Tier 6 (seed data) — only after §5.1 is decided; zero user-facing urgency since it's dev/test-only.

## 9. Phase 5 — backend production strings, LLM prompt direction, `REAL_LANGUAGES` — done, 2026-09-25

**Production strings**: `prompts.constants.ts`'s 10 profile prompts translated meaningfully (not word-for-word — e.g. "بهترین شب من وقتیه که…" → "My best night is when…"), matching their own already-English `id`s. `conversational-setup.service.ts`'s 5 `OPENING_QUESTION` greetings (the fixed first message before any user reply exists to match language against) translated to English, since the app's own UI is English and there's no prior user message to follow yet. `profile.service.ts`'s interests-join separator for the embedding text switched from `'، '` (Persian comma) to `', '`.

**`REAL_LANGUAGES`, done together, cross-stack, in one change**: `backend/src/modules/profile/dto/update-profile.dto.ts` and `frontend/lib/queries/profile.ts` both changed from `['فارسی', 'انگلیسی', 'آلمانی', 'فرانسوی', 'عربی', 'ترکی', 'اسپانیایی']` to `['Persian', 'English', 'German', 'French', 'Arabic', 'Turkish', 'Spanish']` — this is a literal, byte-for-byte-validated value on both sides (§7's Discovery-group note flagged this precisely), so translating one side alone would have sent values the other rejects. Also fixes the frontend's own language-picker buttons for free, since `about-me-fields.tsx` renders `{lang}` directly as both the button's value and its visible label.

**LLM prompt direction — revised twice, the second time on explicit user correction.** First pass changed every "reply in Persian" instruction to "reply in English," matching a literal reading of "جهت پرامپت‌های LLM از فارسی به انگلیسی." The user then corrected this directly: **"کاربر میتونه با هر زبانی حرف بزنه با هوش مصنوعی"** (the user can talk to the AI in any language) — a real product decision, not a wording preference, requiring a second pass:

- `openai-transcription.provider.ts` (shared by AI Search voice input and Conversational Setup voice input): the `language` field sent to real Whisper is no longer set at all (previously forced `'fa'`, briefly `'en'`) — omitting it lets Whisper auto-detect whatever language the user actually spoke, per OpenAI's own API reference.
- `openai-conversational-extraction.provider.ts` (Conversational Setup — this is the one surface that's literally "talking to the AI"): the system prompt now instructs the model to detect the user's language fresh each turn and always reply in that same language, rather than a fixed one. The birthDate calendar-display example (`"Persian calendar 1370/5/12 → Gregorian 1991-07-30"`) is now explicitly flagged as illustrating structure only, to be rendered in the reply's own language.
- `openai-extraction.provider.ts` (AI Search): the system prompt now accepts a search prompt in any language, but explicitly normalizes two outputs to English/Latin regardless of the prompt's own language — `city` (e.g. a Persian-script "تهران" becomes "Tehran") and `semanticQuery` — because both are matched/embedded against real stored profile data, which is English (`ai-search.service.ts`'s `city` filter is a plain `contains`/`insensitive` substring match; `semanticQuery` feeds `text-embedding-3-small` similarity search against English bios). A non-English city or semanticQuery would silently never match anything real, a self-inflicted regression a same-language reply doesn't have.
- `openai-match-explanation.provider.ts` was deliberately left forced to English — this is app-generated UI copy (a "why you two might click" blurb), not a live conversation the user drives, so it follows the app's own display language regardless of what language either profile's bio happens to be written in.

**A real, measured Whisper auto-detect finding, from running the real e2e suite, not assumed**: with `language` no longer forced, Whisper's auto-detect mode sometimes transliterates spoken Persian into Latin script instead of native Persian script — a real captured transcript was `"Ismam Sora hast wa tuye Taharon zindagi mikonam."` for speech saying "اسمم سارا هست و توی تهران زندگی می‌کنم." This is a genuine vendor quirk for this specific language under auto-detect, not an application bug, and not fixable without re-forcing a single language (which would defeat the multilingual requirement) — documented in `docs/roadmap.md`'s Watch items, and the one affected e2e assertion loosened to accept either script.

**Backend e2e re-verification, all three affected real-vendor suites run for real against live OpenAI/Whisper, not assumed clean**: the first real run (already against the multilingual-revised prompts above) surfaced exactly 2 real failures in `conversational-setup.e2e-spec.ts` — the birthDateDisplay mixed-language wording and the Whisper auto-detect transliteration, both described above — both root-caused from the real captured output and fixed as loosened, honest assertions rather than re-forcing determinism the real product no longer wants. After the fix: `conversational-setup.e2e-spec.ts` 10/10, `ai-search.e2e-spec.ts` 10/10 (needed one line changed — `expect(filters.city).toContain('تهران')` → `'Tehran'`, matching the new city-normalization instruction; every other Persian-language test prompt/bio in this file needed no change at all, since multilingual input is now the intended, supported behavior), `match-explanation-boost.e2e-spec.ts` 10/10 (needed one regex changed from Persian fabrication-detection words to their English equivalents, since the explanation output is always English regardless of the profile bios' own language).

**Unit tests updated alongside, all mocked (no real vendor calls, so no run-to-run non-determinism to chase)**: `conversational-setup.service.spec.ts`, `openai-conversational-extraction.provider.spec.ts`, `profile.service.spec.ts`, `openai-extraction.provider.spec.ts`, `ai-search-extraction.service.spec.ts`, `openai-transcription.provider.spec.ts` — arbitrary Persian mock content translated to English throughout (matching the exact same "translate arbitrary test data, preserve real backend/seed-data content" discipline as the frontend e2e pass in §8); `grounding-entity-check.ts` and its own dedicated spec deliberately left untouched — that file's Persian/Arabic letterform normalization is data-matching logic still needed for any free-text a global user might enter, not display text, and its test fixtures are Persian *on purpose*, to exercise that exact normalization.

**Verified**: backend `tsc --noEmit` clean, `eslint` clean (frontend's own `tsc`/`eslint` also re-confirmed clean after the `REAL_LANGUAGES` change). Full backend unit suite: 54/54 suites, 477/477 tests, run twice (once after each prompt-direction revision). All three affected backend real e2e suites: 30/30 tests, run against live OpenAI, Whisper, ClamAV, and MinIO — not mocked, not assumed. Every other backend e2e suite confirmed to reference none of the changed files or values, so was not re-run.
